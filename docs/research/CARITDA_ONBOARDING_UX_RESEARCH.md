## 요약

**권장안은 C: 한 장의 최소 첫 안내 + 해당 기능을 쓸 때의 짧은 설명 + 언제든 다시 여는 사용법이다.** 세 화면으로 모든 기능을 암기시키는 방식은 기본값으로 삼지 않는다. 이는 근거를 종합한 설계 제안이며 CARITDA 사용자 실험에서 입증된 결과가 아니다.

- 최종 서비스 목적은 **자동 확인 → 쉬운 설명과 다음 행동 → 기록 확인 → 인계·조치**다. 최종 목적을 현재 완성 기능으로 표현하지 않는다.
- 최신 앱에는 이름 기반 운전자, 수동 문제·인계·상담 기록, 실제 SDK의 **수동 단발 조회**가 있다. 자동 이상 감지·자동 문제 생성·상시 수집·경고등 통역사·AI 분석은 현재 구현으로 확인되지 않았다.
- 홈에서 먼저 답할 질문은 ‘앱이 무엇을 확인할 수 있나 / 저장된 문제가 있나 / 지금 무엇을 할 수 있나’다. 현재는 ‘자동 확인 미지원’을 숨기지 않으면서 저장된 기록을 찾기 쉽게 한다.
- SDK·Capability·세션·원본·오류 코드 등은 삭제하지 않고 **불러오기 상세**로 옮긴다. 갱신 시각과 에뮬레이터 출처처럼 오해를 막는 정보는 기본 화면에도 남긴다.
- 사용법을 보지 않았다는 이유로 기존 기록 접근을 막지 않는다. 다만 기록 주체 선택과 실제 플랫폼 입력 제한은 튜토리얼 건너뛰기와 별개다.

### 이 작업의 범위와 근거 표시

- **확인 사실:** 공식 공개 문서·그림, 최신 저장소 문서·코드를 읽어 확인한 내용.
- **설계 제안:** CARITDA에 맞게 새로 작성한 구조·문구·행동·인수기준.
- **검증 가설:** 이해도·완료 시간·실수 감소 등 실제 사용자 시험이 필요한 효과.
- 이번 작업은 조사 문서 한 개만 추가한다. 기존 문서·앱 소스·DB·SDK·설정은 수정하지 않는다. 빌드·앱 실행·실차·사용자 시험을 수행하지 않았다.
- 공식 사례는 실차 최초 실행을 재현한 것이 아니라 공개 설명서와 공식 UI 예시를 확인한 것이다. **미확인은 기능 없음과 다르다.**
- 아래 민수·지영, 기록 건수와 SOC 15%는 설명을 위한 예시이며 실제 사용자/차량 측정값이 아니다.

## 1. 최신 구현 확인: 이전 조사와 달라진 점

필수 자료 여섯 개를 확인했다: 기존 UI 연구 [R1], 통합 검토 [R2], UI_ACCEPTANCE [R3], CODEX_PROGRESS [R4], 앱 README [R5], MainActivity [R6]. 실제 읽기의 범위를 구분하기 위해 PleosReadClient [R7], CarSafetyGate [R8], Manifest [R9]도 확인했다. 코드·문서 링크는 조사 시작 커밋에 고정한다.

| 항목 | 최신 코드·문서에서 확인한 상태 | 일반 운전자에게 약속할 수 있는 범위 |

| 자동 이상 감지·자동 사건 기록 | 현재 경로에서 미구현 | ‘자동으로 문제를 찾는다/고장을 기록한다’고 현재 기능처럼 설명 금지 |

| 경고등 통역사·AI·운전 점수 | 현재 화면/구현으로 확인되지 않음 | 작동하는 기능처럼 버튼·튜토리얼·점수·가짜 경고를 넣지 않음 |
| 별도 첫 안내·사용법 화면 | MainActivity 전체에서 전용 화면·재보기 경로를 찾지 못함 | 운전자 선택 첫 화면과 반복 안내 문구는 있으나 독립 온보딩/도움말과 구분 |

현재 Manifest는 DO 미선언이며 CarSafetyGate는 requiresDO=false와 BASELINE을 함께 확인한다. 이는 정차용 앱의 보수적 입력 게이트이지 물리적 기어 P 인증은 아니다. [R8] [R9]

### 1.2 이전 연구를 다시 쓰지 않는 이유

기존 UI 연구 [R1]의 A/B 즉시 전환 문제는 최신 이름 선택·시작 흐름에서 이미 개선됐다. 차량 탭도 실제 단발 조회와 함께 존재한다. 따라서 이를 ‘아직 만들어야 할 기능’으로 반복 제안하지 않는다.

이번 연구의 새 범위는 다음이다.

1. 기존 구조 위에서 **최초 목적 이해·도움말 발견성**을 개선한다.
2. 기술 검증용 정보와 일상 이용 정보를 분리한다.
3. 자동 감지의 최종 지향점과 현재의 제한을 오해 없이 표현한다.
4. ‘정상’, ‘읽음’, ‘해결’, ‘편의 알림’을 구분하는 문구를 만든다.
5. 일반·고령·비전공 사용자가 혼자 수행할 과제와 검증 기준을 제시한다.

통합 검토 [R2]의 사건 연속성·출처/결측 보존·상시 진단 과장 금지 원칙은 유지한다. 신규 SDK 수신은 최신 코드와 기록을 우선한다.

### 2.3 화면 출처와 실제 확인 범위

- 현대 초기설정 시작/나중에 공식 이미지 [I1], Genesis 이상 시스템 상세 공식 예시 [I2], Tesla 경고 상세 진입 도해 [I3]는 통합 작업에서도 이미지 응답을 열어 시각 확인했다.

**판단:** 전체 기능을 미리 설명하기보다 현재 과업을 이해시키는 데 필요한 정보를 그 시점에 제공하는 방향이 타당하다. 다만 생소한 서비스의 목적과 오해하기 쉬운 한계는 최초 방향 안내가 필요하다. 따라서 C를 우선 검증한다.

## 5. C. A/B/C 비교와 권장 온보딩

| 항목 | A: 최초 3단계 | B: 상황별만 | C: 최소 첫 안내+상황별 |
|---|---|---|---|
| 장점 | 전체 목적을 한 번에 설명, 독립적인 필수 설정에는 유용 | 현재 과업 옆에서 바로 적용, 불필요한 선행 읽기 감소 | 첫 방향과 실제 사용 도움을 분리 |
| 단점 | 시작 전 읽기·넘기기·암기, 건너뛴 뒤 회수 어려움 | 서비스 목적·한계·첫 행동을 모를 수 있음 | 첫 안내와 팁을 중복하면 설명 과다 재발 |
| 초보 이해도 | 읽었다는 사실만으로 이해를 보장 못 함 | 첫 화면의 명확성·도움 발견성에 크게 의존 | 목적/지원 범위를 먼저 알고 과업에서 재확인할 가설 |
| 입력 부담 | 안내 진행 조작 추가 | 적은 선행 조작, 도움 탐색 비용 가능 | 한 장을 닫거나 건너뛴 뒤 실제 설정만 |

세 방식의 비교는 설계 판단이다. CARITDA에서 A/B/C 대조실험을 했거나 C가 안전 인증을 받았다는 뜻이 아니다.

### 5.1 첫 안내는 한 장만

**제목:** 내 차 기록을 한곳에서  
**본문:** 차에서 불러온 값과 직접 남긴 문제를 함께 볼 수 있어요.  
**현재 한계:** 지금은 차량의 이상을 자동으로 찾아주지는 않아요.  
**주 버튼:** 운전자 선택  
**보조:** 안내 건너뛰기

- 신규 실행의 두 버튼은 설명을 마친/건너뛴 차이만 남기고 기존 운전자 선택으로 연결한다. 건너뛰기가 가짜 운전자 확정이나 안전 제한 해제를 뜻하지 않는다.
- 이미 확정된 사용자가 사용법에서 다시 열면 ‘닫기’로 이전 화면·초안 맥락으로 돌아간다. 운전자를 재선택시키지 않는다.
- 자동 넘김·시간 제한·권한 요청·메일/휴대폰/QR 로그인은 추가하지 않는다.
- 첫 안내는 OS 사용자별 앱 설치 공간에서 한 번만 제안한다. 운전자 전환마다 팝업을 반복하지 않는다.
- 안내 완료/건너뛰기 상태는 버튼 동작 뒤에만 저장한다. 제한 전환·앱 종료로 중단했으면 완료로 처리하지 않는다.
- 앱 버전이 올라갈 때마다 다시 띄우지 않는다. 지원 범위가 실제 달라질 때 별도의 안내 버전을 검토한다.
- 첫 안내를 생략해도 **홈의 현재 지원 범위**는 계속 보인다. 중요한 한계를 ‘읽었어야 알 수 있는 것’으로 만들지 않는다.

| 직접 증상 기록 | 필요. 빈 기록 목록/첫 작성 | ‘차에서 느낀 소리나 떨림을 남겨 보세요.’ | ‘고장 이름을 몰라도 괜찮아요.’ |
| 다른 운전자에게 인계 | 필요. 다른 사람 기록을 처음 열 때 | ‘같은 앱을 쓰는 다른 사람이 남긴 기록이에요.’ | ‘읽었다면 “내용을 읽었어요”를 눌러 주세요. 수리가 끝났다는 뜻은 아니에요.’ |
| 사용법 다시 열기 | 필요. 고정 진입점, 첫 안내 마지막 단서 | ‘도움이 필요하면 “사용법”을 열어 보세요.’ | 재보기로 기록·설정·운전자 상태가 초기화되지 않음 |

자동 뜨는 말풍선을 여러 개 순서대로 따라가게 하지 않는다. 기본 한 줄은 과업 옆에 두고, 자세한 설명은 ‘왜 필요한가요?’처럼 사용자가 요청할 때 연다. 도움말을 닫았다는 이유로 저장·시작을 실행하지 않는다.

### 5.3 사용법 화면

홈의 ‘사용법’과 공통 메뉴의 동일한 위치에서 접근한다. 일반 이용자가 개발 메뉴를 뒤질 필요가 없어야 한다.

- 기록할 사람 고르기
- 차량값 불러보기
- 느낀 문제 남기기
- 다른 사람의 기록 읽기
- 정비할 때 기록 보여주기
- 자동 확인 기능의 현재 범위

각 항목은 목적 한 문장→해야 할 행동→필요할 때 상세 순서다. ‘처음 안내 다시 보기’도 제공한다. 앱 삭제·데이터 초기화·로그아웃·차량 초기화를 요구하지 않는다.

## 6. D. 상태·경고·오류의 한국어 문구

다음은 타사 문구를 복사한 것이 아니라 CARITDA용으로 새로 쓴 제안이다. 실제 화면 폭·한글 확대·이해도 시험 전의 초안이다.

### 6.1 자동 확인의 세 상태를 분리

| 상태 | 표시 문구 예 | 조건과 금지 사항 |
|---|---|---|
| **현재 감지 기능 미지원** | ‘차량 문제를 자동으로 찾는 기능은 아직 제공되지 않아요.’ | 현재 빌드의 기본 상태. 충전량·거리 수신만으로 정상/감지 완료로 바꾸지 않음 |
| **아직 확인하지 못함** | ‘아직 확인하지 못했어요.’ + ‘새 값을 받지 못해 지금 상태는 알 수 없어요.’ | 향후 확인 기능이 실제 존재하지만 미조회·실패·오래됨·범위 누락일 때. 이유·재시도 가능 여부 구분 |
| **확인된 이상 없음** | ‘확인한 항목에서는 이상이 발견되지 않았어요.’ + 확인 항목·시각 | **향후 기능에만 해당.** 허용된 규칙/범위, 유효·최신 데이터, 성공한 판정이 모두 있어야 사용. 차량 전체 정상 보증 아님 |
| **확인 범위의 안내 있음** | ‘확인할 알림 1건이 있어요.’ + 알림 종류와 다음 행동 | 충전 안내·사용자 기록·검증된 차량 경고를 구분. 모든 알림을 고장이라고 부르지 않음 |

‘정상’, 녹색 체크, ‘문제 0건’을 자동 감지의 성공 상태처럼 보여주지 않는다. **저장된 기록이 0건인 것과 차량의 이상이 없는 것은 다르다.**

### 6.2 고장 경고·편의 알림·사용자 기록

| 종류 | 예시 문구·행동 | 해석 |
|---|---|---|
| 충전 편의 알림 | ‘충전량이 적어요.’ / ‘다음 충전 계획을 확인해 보세요.’ | SOC 15%는 예시이며 배터리 고장 진단이 아님. 임계값·지원 차종·freshness·사용자 설정 검토 후 별도 구현 |
| 사용자 증상 | ‘지영님이 소음 기록을 남겼어요.’ / ‘언제 어떤 소리가 났는지 살펴보세요.’ | 다른 사람의 관찰. 고장 원인·심각도를 앱이 확정한 것이 아님 |
| OEM 차량 경고 | 검증된 차량 경고 이름 + 해당 차량 공식 안내에 근거한 행동 | 현재 자동 기능으로 제공하지 않음. OEM 신호·정의·권한을 검증한 경우에만 사용 |
| 즉시 정차 수준 | ‘안전한 곳에 차를 세우고 차량의 안내를 따라 주세요.’ | **실제로 OEM이 정차를 요구한 경고에만** 사용. 모든 소음·통신 실패·충전 부족에 일괄 적용 금지 |
| 앱 연결/저장 문제 | ‘지금은 차량값을 불러오지 못했어요.’ / ‘저장하지 못했어요. 작성 내용은 남아 있어요.’ | 차량 고장이 아니라 앱의 조회/저장 문제. 마지막 문장은 초안 보존 성공을 확인했을 때만 사용 |

경고 색은 출처·심각도 검증 후 보조로 사용한다. 현재 사용자 기록의 ‘경고등’ 선택 하나만으로 빨간 OEM 경고를 만들지 않는다. 정차·견인·계속 주행 판단을 새 알고리즘 없이 생성하지 않는다.

### 6.3 빈 상태·조회 상태·오류

| 상황 | 권장 문구 | 행동/주의 |
|---|---|---|
| 기록 0건 | ‘아직 남긴 기록이 없어요.’ / ‘차에서 느낀 문제가 있으면 남겨 보세요.’ | ‘문제 남기기’. 정상 판정으로 표현하지 않음 |
| 최초 차량 조회 전 | ‘아직 불러온 차량값이 없어요.’ | ‘차량값 불러오기’. 자동 진단 시작이라고 부르지 않음 |
| 과거 값만 있음 | ‘이전에 불러온 값을 보여드려요.’ | 시각·오래됨 표시. 현재 값으로 오인시키지 않음 |
| 조회 중 | ‘차량 정보를 불러오는 중이에요.’ | 반복 클릭 방지. initialize 반환만으로 연결/조회 성공 표시하지 않음 |
| 일부 항목만 수신 | ‘불러온 정보를 확인해 보세요.’ + 항목별 미지원/실패 표시 | 3항목 모두 정상/전체 차량 정상으로 묶지 않음 |
| 지원하지 않는 항목 | ‘이 차량에서는 연료 정보를 확인할 수 없어요.’ | 같은 조회 반복을 유도하지 않음. 에뮬레이터라면 그 출처도 명시 |
| 권한 없음 | ‘이 항목을 불러올 권한이 없어요.’ | 해결 가능한 공식 절차가 있을 때만 안내. 보안 설정 해제/우회 권고 금지 |
| 시간 초과·연결 실패 | ‘응답을 받지 못했어요. 잠시 뒤 다시 시도해 주세요.’ | ‘다시 불러오기’. 실제 원인이 고장이라고 단정하지 않음 |
| 유효하지 않은 값 | ‘사용할 수 있는 값을 받지 못했어요.’ | 이전 유효 값이 있으면 별도 과거 값으로 표시. null/오류를 0으로 바꾸지 않음 |
| 오래된 값 | ‘지금 상태가 아닐 수 있어요. 마지막으로 불러온 때를 확인해 주세요.’ | 필요 시 ‘새로 불러오기’. 10분 기준은 앱 표시 정책이지 OEM 고장 기준 아님 |
| 저장 실패·보존 성공 | ‘저장하지 못했어요. 작성한 내용은 남아 있어요.’ | ‘다시 저장’ / ‘계속 작성’ |
| 초안 보존도 실패 | ‘작성한 내용을 보관하지 못했어요. 화면을 닫기 전에 다시 확인해 주세요.’ | 보존 성공이라고 쓰지 않음. 기존 확정 기록은 함부로 변경하지 않음 |
| 입력 제한 확인 중 | ‘화면 입력이 가능한지 확인 중이에요.’ | 입력/안내 진행 보류. 사용자가 ‘정차 확인’으로 해제하지 못함 |
| 주행 제한 | ‘지금은 조작할 수 없어요. 안전하게 주차한 뒤 이용해 주세요.’ | OS 차단 우회·위에 그리기·강제 알림 없이 현재 작업 보존 |

### 6.4 제목·버튼·용어 교체

| 현재/기술 표현 | 제안 | 구분 |
|---|---|---|
| 차량 / 차량 상태 | ‘차량 정보’ | 현재는 진단보다 정보 조회라는 성격을 명확히 |
| 차량 데이터 읽고 저장하기 | ‘차량값 불러오기’ | 원래 조회·저장 동작과 수신 기록은 유지 |
| 문제 기록(작성 버튼) | ‘문제 남기기’ | 목록 메뉴 ‘기록’과 행동 이름 구분. 최종 라벨은 과제 시험 후 결정 |
| 전체 문제 n건 | ‘저장된 기록 n건 보기’ | 지금 존재하는 고장 수로 오인하지 않게 함 |
| 미확인 인계 | ‘아직 읽지 않은 전달 기록’ | 읽음 여부와 수리/진단을 분리 |
| 미해결 | ‘관리 중인 기록’ | 내부 상태값은 유지. 해결 확인의 주체를 별도 표시 |
| 운전 시작 | 기존 이름 유지 + ‘이 이름으로 기록을 남겨요’ | 차량 시동 버튼이 아님을 바로 옆에서 설명 |
| Capability | 일반 화면에서 제외, 상세에서는 ‘불러올 수 있는 정보’ 설명 | 기술 원문 값 자체는 그대로 보존 |
| SDK 응답·세션·오류 코드 | ‘불러오기 상세’ 안의 기술 정보 | 일반 사용자가 암기할 용어가 아님 |
| 조치·재발 | ‘점검하거나 한 일’ / ‘다시 발생했어요’ | 전문 용어를 모르는 사용자도 행동을 고를 수 있게 함 |

나이·성별로 이해도를 단정하지 않는다. ‘확인’, ‘시작’, ‘문제’, ‘정상’은 누구나 다른 의미로 해석할 수 있으므로 대상과 결과를 붙여 검증한다.

## 7. E. 개선 화면 구조와 우선순위

### 7.1 홈: 상태 → 다음 행동 → 과거 기록

~~~text
카잇다                         [사용법]
기록 이름: 민수                 [변경]

[현재 확인 범위]
차량 문제를 자동으로 찾는 기능은 아직 없어요.

[기록 요약]
읽지 않은 전달 기록 2건
[전달된 기록 보기]              ← 상황별 주 행동

[이전 기록 보기]    [문제 남기기]
[차량 정보]

홈 | 기록 | 차량 정보
~~~

- 위 ‘자동 확인 미지원’이 현재 구현 상태다. 자동 확인 기능이 생긴 뒤에만 실제 확인 범위·결과·행동을 이 자리에 넣는다.
- 읽지 않은 인계가 있으면 전달 기록, 없고 관리 중 기록이 있으면 해당 기록, 모두 완료됐으면 이전 기록을 우선한다.
- 처음이며 기록도 값도 없을 때는 짧은 빈 상태와 ‘차량값 불러오기’를 주 행동으로 제안한다. 그 버튼이 이상 진단이 아니라는 설명을 함께 둔다.
- 사용자 기록 작성은 보조 행동으로 쉽게 유지한다. 최종 자동 감지 중심을 지향한다고 현재 가능한 수동 기록을 숨기거나 없애지 않는다.
- 홈에 원본 숫자 목록·SDK 세션·상담 전문·분석 그래프를 동시에 펼치지 않는다.

### 7.2 기록: 출처와 처리·읽음 구분

~~~text
기록                           [사용법]
[관리 중] [완료한 기록]         [문제 남기기]

사용자가 남긴 기록 · 소음
민수 · 발견 날짜
아직 읽지 않음                  [내용 보기]

[정비할 때 보여줄 요약]
~~~

상세에서는 사용자 문장→작성자/발견 시각→읽음 행동→점검/해결/재발→시간순 이력 순이다. 현재 데이터의 source는 수동이다. 미래 자동 기록/편의 알림/OEM 경고를 넣더라도 출처·의미를 따로 표시한다. 목록이 없을 때와 조회 실패를 다르게 보여준다.

### 7.3 차량 정보: 기본 카드와 기술 상세

~~~text
차량 정보                      [사용법]
에뮬레이터에서 받은 값이에요. 실제 차량값은 아니에요.

배터리 충전량   [실제 받은 값 + 단위]
마지막으로 불러옴 [시각 / 오래됨]

누적 주행거리   [실제 받은 값 + 단위]
마지막으로 불러옴 [시각 / 오래됨]

제공되지 않는 항목 [펼치기]
[차량값 불러오기]
[불러오기 상세]                 ← 원문·상태·시각·세션 보존
이 값만으로 고장 여부를 판단하지 않아요.
~~~

- 기본 카드당 이름/값/단위 한 묶음, 갱신 상태 한 묶음 정도를 출발점으로 삼는다. 엄격한 두 줄 제한으로 글자를 잘라내지는 않는다.
- 현재 환경에서 제공되지 않는 항목은 별도 행으로 설명한다. 빈 값을 0이나 정상으로 대체하지 않는다. 유효하게 수신한 0.0km는 0으로서 보존한다.
- 최신 시도가 실패했는데 과거 유효 값이 있으면 ‘방금은 불러오지 못함’과 ‘이전 값’을 분리한다. 새 시도 시각을 과거 값의 수신 시각으로 덮어쓰지 않는다.
- 기존 ObservationStore의 시도별 기록·원본·단위·출처·세션은 삭제하지 않는다. UI의 lastAttempt와 lastValid 표시를 분리할 수 있지만 새 정상 판정을 만들지는 않는다.
- 개발자가 필요한 진단 정보는 한 단계로 찾게 하고, 일반 사용자가 내용을 읽어야 다음 버튼을 누를 수 있는 구조로 만들지 않는다.

### 7.4 운전자 선택: 이미 구현된 흐름을 가볍게 설명

~~~text
기록할 사람 선택               [왜 필요한가요?]
[민수] [지영] ... [이름 추가]
이 이름으로 기록을 남겨요.
[민수로 운전 시작]
~~~

신규 이름 등록/후보 선택/시작은 기존 구현을 재사용한다. 별도 회원가입·QR·계정·사진을 도입하지 않는다. 공통 메뉴의 변경 진입은 유지하되 매 화면의 거대한 반복 설명은 줄인다. 작성 화면의 실제 기록 주체는 계속 보여준다. dirty 초안 전환 차단과 당시 이름 snapshot은 유지한다.

## 8. 가독성·작은 창·차량 안전

### 8.1 현재 크기를 유지하면서 정보 계층 정돈

- 현재의 주요 버튼 최소 76dp·24sp는 **CARITDA가 채택한 보수적 목표**로 유지한다. 일괄 법적 의무나 Pleos 정차 앱 공통 필수치라고 주장하지 않는다.
- Google AAOS sizing의 76×76dp는 운전자가 이동 중 쉽게 선택하는 맥락이다. 별도 car-app-quality의 24sp 등은 특정 Tier/카테고리 항목이므로 출처와 적용 범위를 합치지 않는다. [A4] [A5]
- Pleos typography의 12sp 이상 권고는 실제 차에서 12sp면 충분하다는 실험 결과가 아니다. 일반 본문은 기존 24sp 중심, 중요 제목 28–32sp, 꼭 필요한 비핵심 보조는 20sp 정도를 출발점으로 검수한다. [P3]
- 한글 줄 간격은 기본 약 1.3–1.5배를 **제안 출발점**으로 하고, 실제 폰트·기기·확대에서 확인한다. 한국어에 검증된 고정 줄 수·글자 수 상한이라고 쓰지 않는다.
- 텍스트 대비 4.5:1, focus/조작 경계 식별과 색 외 라벨을 검수한다. 이전 연구의 palette·계산을 반복하지 않고 실제 전경/배경·disabled/overlay 상태를 측정한다.
- 전문 로그를 18sp에서 24sp로 전부 키워 일상 화면을 더 길게 만드는 것보다 상세 분리가 먼저다.

### 8.2 작은 창·분할·큰 글씨

- 실제 앱 window의 dp·inset·IME 기준으로 배치한다. 전체 디스플레이 px를 앱 공간으로 간주하지 않는다.
- 단일 열을 기본으로 하고 기존 좁은 창/큰 글씨 메뉴를 재사용한다. 작은 창에 세 탭을 억지로 눌러 넣지 않는다.
- 320/480/600/840/1024dp와 fontScale 100/130/150/200%에서 **홈·기록·차량·운전자·사용법 모두** 확인한다. 기존 검사는 홈 CTA 중심의 부분 검증이라는 점을 유지한다.
- 한글 긴 이름·문장·오류가 줄바꿈되면 버튼 높이를 늘린다. 도움말 닫기/뒤로/주 행동은 스크롤·키보드 상황에서도 접근 가능해야 한다.
- 선택·focus·읽음·사용자 해결 확인을 색 외 텍스트/체크/테두리로 구분한다. TalkBack·키보드·실제 rotary는 각각 검증해야 하며 CSS/모양만으로 통과 처리하지 않는다.

### 8.3 주행/정차 정책

- 현 DO 미선언 정차용 앱의 플랫폼 차단을 유지한다. 첫 안내·사용법·등록·긴 경고 상세를 주행 중 강제로 띄우지 않는다. [P1]
- UNKNOWN/RESTRICTED에서는 안내 진행·이름 확정·조회/기록 확정 등 기존 정책이 막는 행동을 열지 않는다. 이미 입력한 초안과 안내 위치는 보존하고 허용 후 사용자가 재개한다.
- 안내를 건너뛰거나 ‘운전 시작’을 눌러 SafetyGate를 ALLOWED로 바꾸지 않는다.
- requiresDO=false와 BASELINE은 물리 P 인증과 다르다. 추가 차량 신호나 권한을 이번 UX 제안으로 확보했다고 가정하지 않는다. [S1] [S2]
- ‘안전하게 주차 후 이용’은 사용자 안내 문장이지 앱이 주차를 인증했다는 표현이 아니다. OS가 가리면 앱 내 읽기 전용 화면을 계속 볼 수 있다고 보장하지 않는다.
- 미래 DO 주행 조회가 필요하면 별도 Activity/기능 범위·ActiveRestrictions·심사 검토가 필요하다. DO 선언만 추가해서 온보딩을 열지 않는다. [P2]

## 9. F. Codex 구현 지침과 신규 인수기준

**이번 조사에서 구현하지 않는다.** 다음은 별도 후속 작업용이며 기존 AC01–AC28을 대체하지 않는다. 신규 식별자는 ON01–ON24를 사용한다.

### 9.1 구현 순서와 경계

1. 최신 main 및 실제 파일 SHA를 다시 읽는다. 조사 기준 이후 바뀐 SDK·운전자·migration·초안 작업을 보존한다.
2. 우선 UI 표현만 분리한다: 기본 차량 카드 / 불러오기 상세 / 사용법. 원본·단위·시각·출처·실패 이력은 그대로 둔다.
3. 첫 안내 한 장과 명시적 건너뛰기·재보기, 맥락별 짧은 도움을 추가한다. 실제 기능·기록 주체·안전 상태를 바꾸는 동작과 분리한다.
4. 홈의 현재 지원 범위·저장된 기록·다음 행동을 정돈한다. 현재 자동 감지 미지원을 정상으로 포장하지 않는다.
5. 문구·접근성·모든 대상 화면의 작은 창/확대 검수 후 사용자 과제를 수행한다.

금지: mock 경고/점수 추가, 자동 감지 없는 ‘진단 완료’, 반복 수집을 UI 작업에 몰래 도입, SDK/관측 DB 재설계·삭제, 앱 데이터 초기화, 파괴적 migration, 타사 디자인 에셋 복제.

### 9.2 핵심 논리

- onboardingVersion과 완료/건너뛰기 상태는 앱의 도움 표시 상태다. 운전자 confirmed 상태·센서 조회 상태·인계 읽음과 독립이다.
- 사용법 재보기는 저장된 onboarding 상태를 초기화하지 않고 replay 모드로 연다. 닫으면 원래 경로·목록 위치·작성 중 초안으로 돌아간다.
- 현재 detectionAvailability는 미지원으로 표현한다. SDK 수신 완료나 문제 목록 길이로 enabled/정상 여부를 추론하지 않는다.
- 미래 판정은 확인 범위·데이터 유효성·freshness·규칙 결과·출처가 있어야 한다. 이 문서는 그 알고리즘을 구현하거나 임계값을 승인한 것이 아니다.
- lastAttempt와 lastValid를 분리해서 표시한다. 실패한 시도 때문에 과거 값이 현재 정상으로 보이지 않게 한다.
- freshness의 화면 시각 갱신은 재조회/상시 수집이 아니다. 앱이 보이는 동안 시간 경계와 onResume을 재평가하되 SDK 호출을 몰래 반복하지 않는다.
- 실제 수신의 출처 분류를 실차 검증 완료와 동일시하지 않는다. 현재 데모는 에뮬레이터 응답임을 기본 화면에도 표시한다.
- 명시적 저장·읽음·해결·이름 확정의 기존 트랜잭션/중복 방지·snapshot·안전 검사를 유지한다.

## 10. G. 일반·고령·비전공 사용자 검증 계획

### 10.1 대상·환경

- 1차 형성 평가 예: **8명**, 자동차 비전공 운전자. 65세 이상 4명과 그 외 연령 4명을 포함하되 시력·디지털 숙련·공동 차량 경험도 함께 기록한다. 성별이나 연령을 능력의 대리 지표로 단정하지 않는다.
- 실제 구현 전에는 문구/구조 모형으로 이해도를, 구현 후에는 해당 APK로 동선을 본다. 모형·현재 APK·개편 APK 결과를 섞지 않는다.
- 안전하게 정차한 시험 환경 또는 에뮬레이터. 도로 주행 중 튜토리얼·텍스트 탐색 시험은 하지 않는다. 정차 시험으로 주행 안전성을 입증했다고 말하지 않는다.
- 참여자가 혼자 수행하고 관찰자는 버튼 위치를 가르치지 않는다. 진행자가 구제한 경우 독립 성공으로 세지 않는다. 필요한 경우 시험을 중단하며 시간 압박을 주지 않는다.
- 이름·증상은 가상 fixture를 사용하고 실제 개인 기록은 동의 없이 수집·공유하지 않는다.

### 10.2 경로를 알려주지 않는 과제

| 과제 | 관찰할 질문·완료 기준 | 주요 혼동 |
|---|---|---|
| 앱 첫인상 | 앱으로 지금 무엇을 할 수 있고 못 하는지 자기 말로 설명 | 자동 감시·고장 진단이 켜져 있다고 믿는지 |
| 기록 주체 준비 | ‘민수라는 이름으로 기록할 준비를 해 주세요’ | 카드 선택만으로 확정했다고 생각하는지, 차량 시동으로 오해하는지 |
| 안내 건너뛰기 | 건너뛴 뒤에도 기본 기능과 사용법을 찾음 | skip이 이름/안전 제한까지 생략한다고 믿는지 |
| 차량 정보 조회 | 값·언제 받은 값·에뮬레이터임을 설명 | SDK 숫자를 차량 전체 건강 판정으로 해석하는지 |
| 자동 확인 미지원 | 현재 앱이 자동으로 문제를 찾는지 설명 | ‘기록 0건=정상’이라는 결론을 내리는지 |
| 편의 알림 해석 | SOC15% 예시의 뜻과 다음 행동 설명 | 배터리 고장/즉시 운행 금지로 해석하는지 |
| 직접 증상 | 느낀 소리를 남기고 저장 결과 확인 | 고장 이름을 알아야 한다고 생각하는지 |
| 다른 사람 기록 | 지영이 남긴 기록을 읽고 읽음 표시 | 상세를 열기만 하면 읽음 저장되었다거나 수리 완료라고 믿는지 |
| 과거 문제·상담 | 이전 기록과 정비할 때 보여줄 요약을 찾음 | 월간 리포트/공유/정비소 전송이 자동으로 됐다고 믿는지 |
| 실패·복구·재도움 | 조회 실패/오래된 값에서 가능한 행동과 사용법 재접근 | 값 삭제·초기화·보안 해제를 해야 한다고 생각하는지 |

### 10.3 기록 지표와 판단

- 독립 성공/부분/실패, 첫 행동까지의 시간·전체 시간, 잘못 누른 위치, 뒤로/되돌림, 도움 열기·닫기, 구제 여부, 사용자가 말한 의미를 기록한다.
- 과제 후 평이한 난도 질문과 ‘이 화면이 무슨 뜻인가요?’를 묻는다. 클릭 성공만으로 의미 이해를 통과시키지 않는다.
- 숫자는 작은 표본의 **기술 통계**로 보고한다. 8명으로 전체 인구의 안전성·효과 크기나 A/B/C 통계 우월성을 주장하지 않는다.
- 출시 전 중요 목표: ‘현재 자동 감지’, ‘기록 없음=정상’, ‘읽음=해결’, ‘편의 알림=고장’의 중대한 오해가 발견되면 문구/구조를 수정하고 새 참여자로 재검증한다.
- A/B/C를 실제 비교하려면 신규 참여자를 조건별로 배정하고 과제·데이터·기기 조건을 맞춘 별도 실험을 한다. 같은 사람이 A를 학습한 뒤 C를 쓰는 효과를 순수 설계 개선으로 세지 않는다.
- 기존 UI_ACCEPTANCE의 계측 통과는 사용자 이해도 시험을 대체하지 않는다. 반대로 사용자가 잘 눌렀다는 이유로 DB·안전 회귀 검사를 생략하지 않는다.

## 11. 저작권·근거·남은 확인

- 제조사 그림은 비교 연구의 출처 링크로만 제공한다. 앱에 로고·아이콘·이미지·독창적 레이아웃 조합을 복제하거나 재배포할 권리가 확인된 것은 아니다.
- 이 보고서의 CARITDA 문구·정보구조는 별도 제안이다. 일반적인 상태 카드·상세 공개·도움말 패턴은 출처를 밝혀 참고했다.
- 6개 사례의 튜토리얼 단계/skip/재보기/경고 장기 이력 중 미확인 항목은 그대로 남겼다. 리포트·영상·설정 항목으로 대체 증명하지 않았다.
- 직접 자동차에서 A/B/C를 비교한 연구는 확보하지 못했다. 한국어 적정 문장 길이·고령자 이해도·도움말 발견성·안전성은 CARITDA에서 검증해야 한다.
- 타깃 실차·배포 카테고리·지역 UXR·실제 rotary·전체 화면 접근성은 별도 검증 대상이다.
- 조사 기준 뒤 main이 바뀌면 후속 구현은 최신 코드를 다시 읽어야 한다. 이 연구가 이전 작업자의 소스·데이터를 되돌리는 근거가 되어서는 안 된다.

**최종 권고:** ‘Simple is Best’는 필요한 사실을 숨기는 것이 아니라 **지금 상태·다음 행동은 쉽게, 드문 기술 상세는 필요할 때** 보이게 하는 것이다. 현재 없는 자동 감지를 약속하지 않으면서도 최종 서비스의 중심을 센서 숫자 나열이 아닌 문제·행동·기록에 둔다.
