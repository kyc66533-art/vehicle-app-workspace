# CARITDA v0.1 차량용 UI·UX 조사 및 개편 설계

조사·작성 기준: 2026-11-07 (Asia/Seoul)

- 대상: 기존 NextDrive-Pleos의 CARITDA v0.1 로컬 문제 기록·인계 앱.
- 코드 관찰 기준 커밋: **a07d3234cbf6d4f2e7c4e93553e391ff13c652e7**. 이후 코드가 바뀌면 구현 전 재확인한다.
- 이 조사에서 변경하는 저장소 파일: **docs/research/CARITDA_UI_UX_RESEARCH.md 한 개만 새로 추가**.
- 기존 조사 문서, Kotlin 소스, DB, Gradle, SDK 및 에뮬레이터 설정은 이 작업에서 수정하지 않는다.
- CARITDA는 상표 검증 전 가칭이다. 아래 민수·지영과 사건 내용은 **설계용 예시이며 실제 사용자·차량 데이터가 아니다**.

## 0. 결론과 검증 수준

**추천: 정차 전용 v0.1의 기능은 보존하되, ‘홈 / 문제’로 화면을 분리하고 ‘등록된 사람 선택 → 운전 시작’을 기록 주체 확정 절차로 추가한다.**

현재 앱은 실제 차량 센서·AI 진단·휴대폰 전송·정비소 접수가 없는 로컬 수동 기록 앱이다. 따라서 복잡한 자동차 계기판처럼 꾸미거나 SOC·고장 점수·자동 감지 건수를 가짜로 채우는 방향은 피한다.

최소 개편의 우선순위:

1. 누가 기록하는지 알 수 있는 **기록 운전자 선택과 명시적 확정**.
2. 홈의 핵심 행동 한 개, 즉 **문제 기록**을 눈에 띄게 배치.
3. 긴 문제 목록·상세·상담 요약을 서로 다른 화면으로 분리.
4. 인계 ‘읽음 확인’과 실제 정비·해결 판단을 구분.
5. 큰 터치 영역, 읽기 쉬운 글자, 밝은/어두운 테마, 시스템 입력 제한 준수.

| 공식 화면 | Pleos 분할 화면, 현대 ccNC 프로필, Polestar 2 프로필의 공식 이미지 응답과 그림을 직접 확인. 다른 사례의 확인 범위는 2절에 구분 |

## 1. 현재 v0.1에서 유지할 기능과 바꿀 구조

현재 구현 근거: [MainActivity 고정 커밋][C1], [CarSafetyGate 고정 커밋][C2], [Manifest 고정 커밋][C3], [기존 v0.1 사용·검증 문서][C4].

### 1.1 코드에서 확인되는 UI

- 화면 열거는 HOME, RECORD, DETAIL, SUMMARY의 네 종류다.
- MainActivity 97–111행: 앱 이름·설명·A/B 운전자 버튼·입력 제한 설명을 모든 화면 상단에 반복한다.
- 100–104행: 운전자 버튼을 누르면 바로 selectDriver를 호출한다. 선택 후보와 확정 상태가 분리되어 있지 않다.
- 130–158행: 홈에 현재 운전자, 저장 범위, 새 문제, 상담 요약, 미해결 목록, 해결 기록 토글, 출처 설명이 함께 쌓인다.
- 161–198행: 증상 종류, 발생 상황, 발견 시각, 선택 메모를 입력하고 저장한다.
- 201–237행: 상세에서 인계 확인·조치 메모·상태 변경·재발·요약·이력을 제공한다.
- 301–305행: 기본 버튼은 최소 높이 64dp, 글자 20sp다. 이를 곧바로 법규 위반이라고 판정할 근거는 없다. 다만 본 설계의 보수적 차량 터치 목표인 76dp보다 작다.
- 현재 안전 게이트는 requiresDO=false **및** activeRestrictions=BASELINE일 때만 ALLOWED이며, 연결 실패·미확인은 UNKNOWN으로 닫힌다. Manifest에는 distractionOptimized 메타데이터가 없다.

### 1.2 문제 가설과 대응

| 코드 기반 관찰 | 사용성 위험 가설 | 설계 대응 |
|---|---|---|
| A/B 즉시 전환 | 잘못 누르면 다음 기록의 작성자가 바뀔 수 있음 | 후보 선택과 ‘운전 시작’ 확정을 분리 |
| 이름 등록 화면 없음 | A/B가 실제 사람과 어떻게 대응되는지 기억해야 함 | 이름/별명만 등록하는 로컬 운전자 목록 |
| 동일 상단부 반복 | 작은 앱 창에서 본문이 아래로 밀림 | 짧은 제목줄과 기록 운전자 진입점만 유지 |
| 홈에 긴 목록·다수 버튼 | 처음에 무엇을 눌러야 하는지 모호할 수 있음 | 홈은 요약·주 행동, 목록은 ‘문제’ 화면 |
| 버튼들이 유사한 무게 | 기록/상담/관리의 우선순위가 약함 | 화면당 강조 CTA 한 개, 나머지는 보조 행동 |
| 긴 자유 입력과 이력 | 화면 탐색·읽기 부담이 큼 | 입력은 단계적으로, 상세는 핵심→이력 순서 |

이는 코드 기반 설계 판단이다. 사용자의 성공률·시간·오류율이 실제로 개선됐다는 주장은 하지 않는다.

## 2. 제조사 공식 UI·화면 사례

제조사 전체를 하나의 UI로 일반화하지 않는다. 차종·연식·지역·소프트웨어에 따라 다르며, 화면 이미지의 픽셀만 보고 실제 dp/mm를 추정하지 않는다.

### 2.1 현대 Pleos Connect

- **구조:** 상태 표시줄, 좌측 Driving view, 전역 내비게이션/GNB, 우측 앱 창으로 구분된다. 앱 창은 한 앱 또는 두 앱 분할을 지원한다. [P1]
- **화면 근거:** 현대차그룹 공식 보도의 내비/오디오 분할 화면 [I1]과 내비 화면 [I2]. 분할 이미지 원본은 직접 열어 확인했다. [P3]
- **프로필·안전:** 상태 표시줄의 프로필, 속도·telltale·차량 상태, 공조·GNB는 시스템 영역이다. CARITDA가 자기 창에 이를 복제하지 않는다.
- **가져올 점:** 앱 창 크기에 맞춘 재배치, 현재 맥락의 상시 표시, 주행 핵심 정보와 앱 콘텐츠의 분리.
- **가져오지 않을 점:** OS 프로필 전환, 계기판 경고, 공조 제어, 전체 화면을 소유한다는 전제.

### 2.2 현대 ccNC / Seon

- **구조:** 다페이지 홈과 이전·홈·메뉴 목록의 예측 가능한 탐색, 지원 화면의 분할 패널이 설명서에 제시된다. [H1] [H2]
- **프로필:** 홈→설정→사용자 프로필로 진입하고 이름·이미지·계정·보안 설정을 다룬다. 이는 차량 시스템 개인화다. [H1]
- **화면 근거:** 홈 원본 [I3], 프로필 설정 원본 [I4]. 프로필 이미지를 직접 확인했다.
- **가져올 점:** 사용자의 이름을 먼저 보여주고 상세 설정은 별도 화면에 둔다. 이전 위치로 돌아가는 경로를 고정한다.
- **제외:** 지문·비밀번호·Bluelink·차량 설정 연동을 로컬 이름 등록에 끌어오지 않는다. 공식 공개 자료에서 실제 버튼 dp는 확인하지 못했다.

### 2.3 기아 ccNC

- **구조:** 다페이지 홈, 하단 이전·홈·전체 메뉴, 지원 화면의 분할 패널. [K1] [K2] [K3]
- **프로필:** 운전자 이미지 선택 후 언어·이름 등을 설정하고 Kia Connect 연동을 선택하는 초기 설정 흐름이 있다. 사양·지역별 차이가 있다. [K1]
- **화면 근거:** 홈 [I5], 프로필 변경 [I6], 초기 사용자 설정 [I7]. 공식 매뉴얼과 이미지 출처를 확인했으나 본 조사에서 모든 이미지를 별도 시각 감사한 것은 아니다.
- **가져올 점:** 처음 등록과 이후 전환을 구분한다. 이미 등록한 사람에게 가입 절차를 반복시키지 않는다.
- **제외:** Kia Connect 로그인, 서버 백업, 차량 프로필 권한, 길게 누르기 중심의 핵심 조작.

### 2.4 Volvo Android Automotive 계열

- **모델 구분:** 참조한 XC90 센터 디스플레이 설명은 지도 중심 홈, 미디어·전화 위젯, 하단 차량 진입점을 설명한다. [V1]
- **프로필:** 차량 프로필·Volvo ID·차량 키의 연계는 시스템 기능이다. 앱 내부 기록 운전자와 같지 않다. [V2]
- **그림 출처:** EX40 2026 공식 매뉴얼 PDF [V3]도 제공한다. **EX40 그림을 XC90의 동일 UI라고 합쳐 해석하지 않는다.** 이 문서에서 PDF의 개별 그림을 새 이미지로 추출하지 않았다.
- **가져올 점:** 홈에서 핵심 맥락과 빠른 행동을 보여주고 설정은 분리한다. 제한 상태에는 이유를 설명한다.
- **제외:** 키 감지 자동 전환, Owner/Co-driver 권한, 차량 전체 개인화. 제조사 버튼 dp는 미확인이다.

### 2.5 Polestar 2, 2025 공식 설명서

- **구조:** 최근 앱 네 개의 타일 홈과 상단 프로필/이니셜 진입점. 이 사례를 다른 Polestar 차종의 분할 UI와 섞지 않는다. [O1]
- **프로필:** 차량 내 프로필과 Polestar/Google 계정·물리 키 연결을 별도로 설명한다. [O2] [O3]
- **화면 근거:** 홈 네 타일 [I8], 프로필 선택 [I9]. 프로필 선택 원본을 직접 열어 확인했다.
- **가져올 점:** 이름/별명과 선택 상태를 큰 단위로 보여주고 현재 사용자를 쉽게 다시 찾게 한다.
- **제외:** 계정 로그인·키 연결·관리자 권한을 CARITDA 등록 필수 단계로 만들지 않는다.

### 2.6 Tesla Model Y

- **공식 자료:** Driver Profiles [T1]는 로컬 프로필과 Tesla Profile·키 연계를 구분하며, Touchscreen Overview [T2]는 화면 구조와 그림의 공식 출처다.
- **확인 한계:** 조사 중 설명서/검색 자료를 참고했으나, Touchscreen 페이지를 이 문서 작성 단계에서 재조회할 때 **HTTP 403**이었다. 별도 화면 원본 이미지와 실제 dp는 확보하지 못했다. 따라서 이미지 색·크기 수치를 검증했다고 쓰지 않는다.
- **가져올 점:** 사용자의 이름을 명확히 표시하고 로컬 상태와 계정 동기화 범위를 구분한다.
- **제외:** Tesla 클라우드 프로필·차량 키·시트 설정. Valet/속도 제한 기능을 일반적인 ‘주행 중 프로필 전환 금지’의 근거로 대신 쓰지 않는다.

### 2.7 비교에서 얻은 CARITDA 원칙

1. **현재 사람은 쉽게 보이고, 관리 화면은 따로 둔다.**
2. 기능별 메뉴 위치를 고정하고 제스처·숨은 길게 누르기를 필수로 만들지 않는다.
3. 시스템 경고·주행 정보와 사용자 작성 기록을 혼동시키지 않는다.
4. CARITDA는 계기판이 아니라 **증상→인계→조치/재발→상담**의 기록 도구다.
5. 외형을 복제하지 않고 계층·상태 표현·탐색 원리만 참고한다. 제조사 이미지·로고·아이콘을 앱 자산으로 무단 재사용하지 않는다.

## 3. AAOS / Pleos 안전·접근성 기준

### 3.1 적용 범위를 혼동하지 않기

| 구분 | 의미 | CARITDA 적용 |
|---|---|---|
| Android for Cars 템플릿 앱 | CarAppService의 Screen/Template를 호스트가 렌더링 | 현재 자체 Activity와 다름. 템플릿의 breakpoint·폰트를 곧바로 의무라고 쓰지 않음 |
| 커스텀 AAOS/Pleos Activity | 앱이 View/Compose로 직접 UI 구성 | 현재 앱. 입력 제한·focus·inset·가독성을 직접 구현해야 함 |
| 플랫폼/배포 준수 | DO 선언, 제한 기능 처리 등 공식 요구 | 앱 배포·동작 기준이며 법률 자체와 동일하지 않음 |
| 디자인 권고 | 터치 크기·간격·glanceability 등 | 출처와 적용 대상을 밝히고 보수적으로 채택 |
| CARITDA 제안 | 아래 24sp·76dp·화면 구성 등 | 프로젝트 설계 목표. 제조사 실측치나 법적 의무 아님 |

### 3.2 수치와 단위

| 항목 | 공식 자료 | 이 앱의 제안 |
|---|---|---|
| 터치 영역 | Google Cars sizing: 최소 76×76dp [G1] | 핵심 버튼·탭·운전자 카드의 실제 클릭 영역을 최소 76×76dp로 설계 |
| 타깃 간격 | Google visual principles: 가능하면 23dp [G2] | 인접 주요 행동은 가능하면 24dp. 좁은 창에서는 무리한 3열 대신 재배치 |
| 글자 | Android Auto 본문 기준은 24dp. Pleos는 12sp/18px 하한 및 일반 3mm·핵심 4mm 등을 권고 [G3] [P4] | 제목 28–32sp, 본문·주 버튼 24sp, 비핵심 보조 20sp를 출발점으로 실제 HMI에서 검수 |
| 대비 | Pleos는 4.5:1 이상 권고 [P2]. AAOS Car UI는 텍스트 4.5:1, 버튼/배경 3:1 등 [G4] | 정보 텍스트 4.5:1 이상, 조작 외곽·focus 구분 3:1 이상을 목표 |
| 확대 | Android 14는 최대 200% 글자 확대 [G5] | 모든 글자는 sp, 크기·간격은 dp. 100/130/150/200%에서 잘림·겹침 검사 |
| 화면 크기 | Google adaptive car UI 및 Pleos 가변 창 가이드 [G6] [P1] | 디스플레이 전체 px가 아닌 실제 앱 window의 dp·inset으로 레이아웃 결정 |

- 24dp라는 Android Auto 문서 값을 곧바로 모든 sp와 동치라고 주장하지 않는다. CARITDA는 사용자 확대를 존중하기 위해 sp를 사용한다. [G7]
- 3/4mm는 실제 패널 밀도·관찰 환경 없이 스크린샷에서 검증할 수 없다. 필요하면 패널 PPI와 렌더링 px로 물리 크기를 확인한다.
- 제조사의 버튼 물리 치수와 공개되지 않은 UI token은 추정해서 채우지 않는다.

### 3.3 정차·주행 상태

**requiresDistractionOptimization=false는 기어 P와 동치가 아니다.** 현재 게이트가 BASELINE까지 확인하더라도 이는 플랫폼의 화면 입력 허용 상태이지 물리적인 주차 인증이 아니다. OEM·지역·display·정책에 따라 매핑이 달라진다. [G8] [G9] [G10]

**최소 개편 M0는 현재처럼 DO 미선언의 정차 전용 앱을 유지한다.**

- OS가 주행 중 Activity를 가리거나 막는 동작을 우회하지 않는다.
- 앱 내부에서 읽기 전용 홈으로 바뀌더라도 OS 차단보다 우선하여 계속 표시된다고 보장하지 않는다.
- 입력 허용 상태가 새로 확인되기 전 UNKNOWN에서는 운전자 전환·등록·문제 확정 저장·인계 확인·상태 변경을 모두 막는다. 이미 입력한 값을 잃지 않기 위한 비확정 로컬 초안 cache flush만은 별도이며, 문제/event/확인 이력을 생성해서는 안 된다.
- RESTRICTED로 바뀌면 키보드·대화상자를 닫고 작성 중 값을 보존한다. 저장 성공처럼 표시하지 않는다.
- ALLOWED로 돌아와도 운전 시작·저장·인계 확인을 자동 실행하지 않는다.
- ‘운전 시작’ 버튼은 앱의 기록 주체 확정일 뿐이다. 안전 게이트를 ALLOWED로 바꾸거나 실제 차량 상태를 변경하지 않는다.
- 한국을 Pleos 공개 표의 ‘Other regions’로 임의 고정하지 않는다. 대상 환경의 실제 UXR callback과 bitmask를 확인한다. [P5]

### 3.4 향후 주행 중 조회가 필요할 때만 별도 검토

정차 전용 M0에 distractionOptimized=true만 붙여 주행 중 모든 화면을 여는 방식은 금지한다.

확장 시에는 주행 허용 화면/Activity를 분리하고 현재 ActiveRestrictions를 기능별로 처리한다. 예: NO_KEYBOARD, NO_FILTERING, NO_SETUP, NO_VIDEO. 폼·프로필 관리·정비 요약의 긴 글 읽기는 주행용 핵심에서 제외한다. 최종 허용 범위는 대상 Pleos의 플랫폼·배포 심사를 확인해야 한다. [P6] [G8] [G11]

### 3.5 입력·접근성

- 토스트만으로 오류를 알리지 않는다. 필드 옆 오류와 화면 내 저장 상태를 유지한다.
- 색만으로 현재 선택·미확인·오류를 구분하지 않는다. 체크, 라벨, 아이콘, 테두리를 함께 쓴다.
- 아이콘 단독 핵심 버튼을 피한다. ‘확인’, ‘변경’ 대신 가능하면 ‘읽음 확인’, ‘운전자 변경’처럼 대상을 쓴다.
- 버튼의 disabled 투명도를 낮추는 것만으로 사유를 전달하지 않는다. 잠금 사유 문구는 읽을 수 있는 대비를 유지한다.
- 접근성 읽기 순서는 제목→기록 운전자→요약→핵심 행동→목록→탐색 순으로 고정한다.
- 키보드/rotary focus가 사라지거나 막다른 곳에 갇히지 않게 한다. 선택과 focus는 다른 시각 상태다.
- rotary 대상 장비와 Car UI library를 사용하는 경우 공식 FocusParkingView/FocusArea 구조를 검토한다. 이름만 흉내 낸 가짜 View를 추가하지 않는다. 실제 HMI rotary 검증은 별도다. [G12]

## 4. 운전자 등록·선택·전환 설계

### 4.1 OS 계정과 앱 내부 기록 운전자

| 항목 | 차량 OS 프로필 | CARITDA 기록 운전자 |
|---|---|---|
| 범위 | Android user·차량 개인화·계정/키 등 | 같은 OS 사용자·앱 설치 공간 안의 로컬 기록 주체 |
| 등록 | OEM·OS 기능 | 이름/별명만 입력 |
| 인증 | 제조사/OS 정책 | 로그인·전화번호·메일·비밀번호를 요구하지 않음 |
| 데이터 | OS 사용자별 앱 데이터가 분리될 수 있음 | 같은 앱 로컬 저장 공간의 문제를 등록 운전자와 무관하게 함께 조회 |
| 차량 제어 | 차량 권한에 따라 제공 | 시동·키·시트·미러·공조를 변경하지 않음 |
| 보안 의미 | OS 권한 경계 | 접근 제어·본인 인증이 아님 |

AAOS OS 사용자가 바뀌어도 SQLite가 자동으로 공유된다고 가정하지 않는다. CARITDA A/B 전환은 같은 OS 사용자 안에서 이루어지는 앱 내부 전환이다. [G14]

권장 안내: **‘이 차량 앱의 기록에 사용할 이름입니다. 차량 계정이나 시트 설정은 바뀌지 않습니다.’**

### 4.2 처음 쓰는 사람

~~~text
앱 실행 → 등록된 운전자 없음
  → [운전자 등록]
  → 이름/별명 입력 → [등록]
  → 운전자 선택 화면에 새 이름이 ‘선택 후보’로 표시
  → [운전 시작]
  → 기록 주체 확정 → 홈
~~~

- 가입·로그인·휴대폰 연동·사진 업로드는 넣지 않는다.
- 이름은 앞뒤 공백 제거, 빈 값/줄바꿈/제어문자 거부. 제안 상한은 사용자 인지 문자 12자이며 기존 기록 본문 길이 제한과 혼동하지 않는다.
- M0의 이름 중복 정책: 앞뒤 공백 제거·Unicode NFC 정규화·Locale.ROOT 소문자 비교 후, 보관되지 않은 기존 이름과 같으면 등록/수정을 막고 구분 가능한 별명을 안내한다. 보관된 이름은 다시 쓸 수 있으나 과거 ID를 재사용하지 않는다.
- 이름을 저장했다고 바로 운전자가 바뀌지 않는다. 등록 후 별도 ‘운전 시작’으로 확정한다.

### 4.3 이미 등록된 사람

~~~text
운전자 선택 화면
  [민수] [지영] ... [운전자 추가]
       ↓ 사람 카드 탭
  ‘지영 선택됨’ + 체크/테두리
  DB의 현재 기록 운전자는 아직 바뀌지 않음
       ↓ [지영으로 운전 시작]
  시작 시점에 안전 상태 재확인
  기록 운전자 확정 → 홈 → 미확인 인계 n건 표시
~~~

- 사람 카드 탭 한 번, 운전 시작 한 번을 기본 경로로 한다. 확정 팝업을 또 반복하지 않는다.
- 선택 후보가 없으면 시작 버튼 비활성화 + ‘사람을 선택해 주세요’.
- 취소/뒤로는 현재 운전자를 바꾸지 않는다.
- 이미 확정된 동일 운전자에게 시작을 연속 눌러도 중복 전환·인계 확인·문제 생성이 일어나지 않는다.
- 홈에서는 **‘기록 운전자: 지영’**을 표시한다. ‘차량 로그인 완료’나 ‘안전 운전 가능’이라고 쓰지 않는다.

### 4.4 재실행·전환 상태

앱의 사람 선택 상태와 차량 안전 상태는 서로 독립이다.

| 앱 사람 상태 | 표시/행동 |
|---|---|
| NO_PROFILE | 등록 안내. 작성·확정 행동 불가 |
| RECENT_UNCONFIRMED | 콜드 스타트 때 최근 사람을 후보로 보여줌. ‘최근 운전자’로 표시하고 시작 전에는 새 기록 작성 주체를 자동 확정하지 않음 |
| CHOOSING | pendingDriverId만 변경. 기존 확정 주체·역사 기록은 불변 |
| CONFIRMED | 기록 운전자 확정. 플랫폼 입력 허용 범위에서 조작 |
| RESTRICTED / UNKNOWN | 위 사람 상태를 보존하되 확정·변경·쓰기 차단. 차량 상태를 사람 선택으로 해제할 수 없음 |

- 창 크기 변경·화면 회전 등 구성 변경은 콜드 스타트와 구분하여 현재 확정 상태를 복원한다.
- 프로세스 종료 후 새 실행에서는 최근 선택을 제안하되 명시적 시작을 다시 받는다. 실제 시동/주행 종료 시각을 추정하지 않는다.
- M0의 ‘운전 시작’은 **이번 앱 이용의 기록 주체 확인**이다. 실제 운행 거리·시간·경로를 수집한 운행 세션으로 표현하지 않는다.
- 운행 세션/거리 통계를 나중에 추가한다면 별도 데이터 모델과 수신 검증이 필요하다. 앱 종료 시각을 실제 주행 종료로 기록하지 않는다.

### 4.5 인계·이력·이름 변경

- 운전자 전환은 기존 문제의 등록자, 조치 작성자, 발견 시각, 인계 확인 이력을 바꾸지 않는다.
- 다른 운전자의 미해결 문제가 있으면 홈에서 ‘미확인 인계 n건’을 보여준다. 시작과 동시에 모두 읽은 것으로 처리하지 않는다.
- 상세를 열었다는 이유만으로 읽음 확인을 저장하지 않는다. **‘내용을 읽었어요’**를 명시적으로 눌러 저장한다.
- 재발/새 revision 이후의 인계 확인은 기존 확인과 구분한다. 해결 여부와 읽음 여부도 분리한다.
- 운전자 이름 변경은 stable ID를 유지한다. 문제 등록과 각 event/읽음 확인에는 **당시 표시 이름 snapshot**을 저장하고 과거 화면·상담 요약의 기본 작성자 이름으로 쓴다. 이름이 달라졌으면 상세에서만 ‘당시 운전자 A · 현재 민수’를 보조 표기한다. 과거 snapshot을 새 이름으로 덮어쓰지 않는다.
- 이력이 있는 사람은 물리 삭제 대신 **보관**한다. 보관해도 과거 문제·확인·조치 이력은 조회 가능해야 한다.
- 현재 확정 운전자를 보관하려면 먼저 다른 사람으로 전환하게 한다. 이력이 연결된 행을 연쇄 삭제하지 않는다.
- M0에서는 수정된 미저장 초안이 있으면 운전자 변경을 막고 ‘작성 중인 기록을 저장하거나 작성 취소한 뒤 바꿔 주세요’와 ‘계속 작성’을 제공한다. 작성 취소는 명시적으로 확인받는다. 새 사람에게 초안을 자동 재귀속하지 않는다.
- ‘초안을 남겨 둔 채 다른 운전자로 변경’하는 기능은 M0에서 제공하지 않는다. 초안 자동 보존 자체는 다음 정책으로 M0에 포함한다.

### 4.5.1 M0 초안 보존의 확정 정책

- 대상은 새 문제, 점검·조치 메모, 재발 메모의 미저장 입력이다. 초안 ID·종류·대상 issue/revision·원 작성자 ID/당시 이름·입력값·갱신 시각을 앱 전용 로컬 cache에 보존한다. 확정 문제/event와 분리하며 GitHub·외부로 전송하지 않는다.
- 입력 변경 때 저장하고 정상 화면 이탈·입력 제한 전환·onStop 때 마지막 값을 flush한다. 구성 변경과 정상 종료 후 재실행에서는 초안/원 작성자를 복원한다. 비정상 전원 상실 직전 아직 flush되지 않은 키 입력까지 보장한다고 주장하지 않는다.
- 재실행 시 ‘민수가 작성 중인 기록이 있습니다’를 표시한다. 원 작성자를 선택하고 운전 시작을 확정한 뒤 ‘계속 작성’한다. 다른 사람으로 시작하려면 기존 초안을 먼저 명시적으로 취소해야 한다. 원 작성자를 새 사람으로 바꾸지 않는다.
- ‘저장 후 변경’: 원 작성자로 확정 저장이 성공한 뒤 초안 cache를 제거하고 운전자 선택을 연다. 실패하면 초안과 현재 운전자를 유지한다.
- ‘작성 취소 후 변경’: ALLOWED에서 취소 확인을 받은 뒤 해당 초안 cache만 제거하고 선택을 연다. 기존 확정 문제/event는 삭제하지 않는다.
- ‘계속 작성’: 전환하지 않고 같은 초안·작성자로 복귀한다. 안전 제한 중에는 입력 대신 초안을 보존하고 해제 후 명시적으로 재개한다.
- cache 쓰기 실패는 ‘초안을 보존하지 못했습니다’로 알리고 조용히 성공 처리하지 않는다. 손상 cache는 원본을 보존한 채 복원 실패를 구분한다. 문제 저장과 cache 제거의 순서/재시도는 중복 확정이 없도록 draft ID로 검증한다.

### 4.6 기존 A/B 데이터 이전

구체적인 DDL은 Codex가 실제 model/repository를 읽고 확정한다. 이 문서는 기존 스키마를 실측한 migration SQL이 아니다.

1. 기존 A/B를 stable legacy ID에 대응시키고 표시 이름만 ‘운전자 A/B’로 초기화한다.
2. 문제 등록자·event actor·인계 확인·revision 관계를 빠짐없이 대응시킨다. 기존 이력의 당시 이름 snapshot은 보존된 A/B 라벨로 backfill하고, 존재하지 않았던 실제 이름을 추정하지 않는다.
3. 이름 편집은 ID를 재생성하지 않는다. 기존 A/B의 의미를 조용히 다른 사람에게 바꾸지 않도록 사용자에게 이름 수정임을 알린다.
4. migration은 트랜잭션·실패 시 롤백·반복 실행 안전성을 갖춘다. drop/recreate로 기록을 지우지 않는다.
5. 이전·이후 문제 수, event 수, 작성자 매핑, 발견/기록 시각, 해결·재발·확인 이력을 대조한다.
6. SQLite 삭제, 앱 데이터 지우기, 앱 재설치를 UI 개편 방법으로 사용하지 않는다.

M0 내비게이션: 홈 | 문제
  홈
    최근/현재 기록 운전자 → 운전자 선택·등록·관리
    미확인 인계 요약 → 문제 상세
    [문제 기록] → 새 문제
    최근 미해결 최대 1~2건 → 전체 문제
  문제
    미해결 / 해결 기록
    문제 카드 → 상세 → 읽음 확인 / 조치 / 상태 / 재발 / 이력
    [정비 상담 요약] → 선택 문제 또는 전체 기록의 범위를 명시

M1 추가 내비게이션: 차량
  차량 상태 → 실제 연동 시 수신값·시각·결측
  경고등 도움말(가칭 경고 통역사) → 공식 설명·출처
  기록 경향 / 운전 분석 → 데이터가 있을 때만 적합한 이름으로 제공
~~~

앱 내부 메뉴는 OS의 GNB·앱 라이브러리와 다른 영역이다. M0에 비어 있는 미래 기능 버튼을 다수 노출하지 않는다.

### 5.2 기능별 배치와 제공 수준

| 기능 | 위치·대표 행동 | M0 최소 개편 | M1/확장 조건 |
|---|---|---|---|
| 차량 상태 카드 | 홈 요약, 차량 상세 | ‘차량 데이터 미연동’ 한 줄. 수동 문제 건수를 정상 판정으로 바꾸지 않음 | 허용 API 실제 수신·시각·freshness 검증 후 값 표시 |
| 자동 감지 / 수동 기록 | 문제 목록의 출처 라벨 | 모든 기존 문제를 ‘사용자 직접 기록’으로 명시 | 자동 감지는 별도 수신/판정 검증 후. 미구현 필터를 정상 작동처럼 노출하지 않음 |
| 증상 기록 | 홈의 주 CTA, 문제 목록 진입 | 기존 종류·상황·발견 시각·메모·저장 유지 | preset 등 입력 단축은 효용 검증 후 |
| 미해결 문제 인계 | 홈 미확인 요약→문제 상세 | 사람·revision별 명시적 읽음 확인 | 모바일/원격 인계는 별도 인증·동기화 과제 |
| 정비 상담 요약 | 문제 화면·상세의 보조 CTA | 현재 로컬 요약 조회 유지, 범위와 ‘미전송’ 명시 | 외부 전송/접수는 사용자 승인·API 검증 후 |
| 경고 통역사 | 차량→경고등 도움말 | 기능 없음. 가짜 진단 카드나 작동하지 않는 메뉴를 넣지 않음 | 공식 설명서 출처·차종 적용성 확인. ‘고장 진단’으로 표현 금지 |
| 운전 분석 | 차량→분석 | 기능 없음. 점수·연비·급가속·SOC 추세를 생성하지 않음 | 수동 사건 집계면 ‘기록 경향’. 실제 운전 분석은 적합한 데이터 수신·정의 검증 필요 |
| 운전자 관리 | 공통 기록 운전자→선택/관리 | 이름 등록·선택·시작·이름 수정·보관 | OS 계정·키·시트 연동은 범위 밖 |

### 5.3 주요 동선

- 등록된 사람이 앱을 처음 확정: 카드 선택→운전 시작→홈, 기본 2회 조작.
- 문제 기록: 홈→문제 기록→입력→저장. 저장 후 상세로 가서 결과 확인.
- 인계 확인: 홈의 미확인 항목→상세→내용을 읽었어요. 전환만으로 자동 확인하지 않음.
- 상담: 문제→상담 요약 또는 상세→이 문제의 상담 요약. 사용자가 어떤 범위인지 알 수 있어야 함.
- 운전자 변경: 공통 진입점→다른 사람 선택→운전 시작. 이전 기록은 그대로 유지.

## 6. 화면별 텍스트 와이어프레임

아래는 앱 창 내부의 구조이며 제조사 화면 크기를 복제한 도면이 아니다. 문구와 데이터는 예시다. 긴 글자는 줄바꿈하고 버튼 높이는 내용에 맞춰 늘린다.

### W1. 운전자 선택·등록

~~~text
[뒤로]       기록 운전자 선택
이 차량 앱의 기록에 사용할 사람을 선택하세요.

[ ○ 민수              최근 선택 ]
[ ✓ 지영              선택됨    ]
[ + 운전자 추가                 ]

선택한 사람: 지영
[       지영으로 운전 시작       ]  ← 강조 CTA
차량 계정·시트 설정은 바뀌지 않습니다.
~~~

- 카드 탭: 후보 선택만. 시작: 안전 상태 재확인 후 확정.
- 등록 폼은 이름/별명 한 필드와 등록 버튼만. 오류는 필드 바로 아래.
- 처음 사용에는 뒤로 가더라도 가짜 A/B 사용자를 자동 생성해 확정하지 않는다. 기존 설치의 A/B는 4.6에 따라 보존한다.
- 입력 제한 시 시작/추가/관리 모두 잠그고 이유를 표시한다.

### W2. 홈

~~~text
CARITDA       [기록 운전자: 지영 · 변경]

미확인 인계 2건
[가속할 때 진동 · 민수가 남김] → 상세

[             문제 기록             ]  ← 주 CTA
미해결 3건              [전체 문제 보기]
최근 문제 1~2건의 간단 카드

차량 데이터 미연동 · 사용자 기록만 표시
[       홈       ] [       문제       ]
~~~

- 미해결 0건: ‘등록된 미해결 문제가 없습니다. 차량 정상 진단 결과는 아닙니다.’
- 시작 전에는 최근 운전자와 ‘운전 시작’이 주 CTA다. 문제 작성은 확정 후 활성화한다.
- 홈에서 전체 이력·긴 상담 요약·분석 그래프를 펼치지 않는다.

### W3. 문제 목록

~~~text
문제              [기록 운전자: 지영 · 변경]
[미해결] [해결 기록]     [새 문제]

미확인 인계 우선
[사용자 기록 · 미해결]
진동 / 가속할 때 핸들이 떨림
발견 11/07 10:25 · 등록 민수
지영의 읽음 확인 필요             [상세]

[정비 상담 요약 · 범위 선택]
[       홈       ] [       문제       ]
~~~

- 목록 정렬은 미확인 인계 우선, 그 안에서는 최근 발견/기록 순을 명시한다. 심각도를 AI가 판정한 것처럼 정렬하지 않는다.
- 카드 제목 최대 두 줄로 미리 보여주되 원문은 상세에 보존한다.
- 해결 기록이 있어도 데이터가 삭제된 것처럼 보이지 않게 개수·필터를 표시한다.

### W4. 새 문제 기록

~~~text
[취소/뒤로]             새 문제
작성자: 지영          사용자 직접 기록

증상 종류 [소음] [진동] [경고등] [기타]
어떤 상황이었나요? [다중행 입력]
발견 시각 [현재 시각 기본값 · 수정]
추가 메모 [선택 입력]

[            이 차량 앱에 저장           ]
차량 센서·AI 진단이 아닌 직접 작성 기록입니다.
~~~

- 스피너를 큰 선택 타깃으로 바꾸더라도 기존 SymptomType 의미를 보존한다.
- 기존 상황/메모 입력 한도를 임의로 낮추거나 원문을 잘라 저장하지 않는다.
- 발견 시각과 등록 시각은 구분한다. 기기 시간대 표시는 요약에도 일관되게 유지한다.
- 저장 중 반복 탭을 막고, 성공 후에만 상세로 이동한다. 실패 시 입력을 그대로 남긴다.
- 키보드가 CTA를 가리지 않도록 IME inset과 스크롤을 처리한다. 안전 제한 발생 시 키보드 종료·초안 보존.

### W5. 문제 상세·인계·조치

~~~text
[문제로]              진동 · 미해결
가속할 때 핸들이 떨림
사용자 기록 · 등록 민수 · 발견/등록 시각

지영의 인계 확인이 필요합니다.
[            내용을 읽었어요            ]

[점검·조치 메모] [상태 변경]
[재발 기록]     [이 문제의 상담 요약]

확인·조치 이력  ↓ 시간순 기록
‘상태는 사용자가 표시한 기록입니다.’
~~~

- 읽음 확인은 접수·점검·해결과 다르다. 한 revision에 중복 확인하지 않는다.
- 해결은 ‘사용자 해결 확인’으로 표현하고 기존 안내·명시적 확인을 유지한다.
- 재발은 원래 이력을 보존하고 새 revision/재발 이력을 연결한다.
- 사용자가 선택한 ‘경고등’이라는 증상만으로 OEM 경고 심각도나 고장 코드를 생성하지 않는다.

### W6. 정비 상담 요약

~~~text
[뒤로]                 정비 상담 요약
범위: 선택 문제 1건 / 미해결 / 전체 기록
기록 운전자·발견/등록 시각·증상·조치·재발·확인

사용자 직접 기록 / 차량 센서 데이터 미수집
기기 시간대: 실제 설정값
외부 정비소에 전송되지 않았습니다.
~~~

- 첫 진입에서 현재 범위를 분명히 표시한다. 기존 전체 요약 조회 능력을 없애지 않는다.
- 공유·접수·PDF 전송 아이콘을 기능이 없는 상태에서 넣지 않는다.
- 긴 요약을 주행 중 읽는 기능은 M0에 포함하지 않는다.

### W7. 차량 상태·경고 도움말 — 확장안 전용

~~~text
차량
차량 데이터: 미연동 / 수신 / 오래됨 / 오류
각 값: 이름 · 값/단위 · 수신 시각 · 출처

경고등 도움말
[사용자가 선택한 경고등]
공식 설명 / 출처 / 적용 차종 / 확인일
고장 진단이나 운행 허가가 아닙니다.
~~~

- 실제 수신 전에는 정상·배터리 양호·타이어압 정상 같은 판정을 표시하지 않는다.
- 허용 API의 실수신·freshness 기준이 결정되지 않으면 센서 값을 넣지 않는다.
- telltale·타이어압 등 공개 API 정책에서 막힌 항목을 UI 구현 명목으로 우회하지 않는다.
- 긴급 행동 안내가 필요하면 대상 차량 공식 설명서의 검증된 안내를 정확히 인용하고 출처를 붙인다. 앱이 새로운 정비·안전 진단을 만들지 않는다.

### W8. 기록 경향·운전자 관리 — 범위 분리

~~~text
기록 경향(선택 확장)
기간 · 사용자 입력 문제 수 · 조치/재발 기록
‘운전 점수’나 ‘안전 등급’이 아님

운전자 관리(M0)
이름/별명          [이름 수정] [보관]
역사 기록은 삭제되지 않습니다.
[운전자 추가] → 이름 입력 → 등록 → 선택 → 운전 시작
~~~

기록 경향과 운전자 관리는 서로 다른 화면이다. 하나의 관리 대시보드에 묶지 않는다. 운전자 관리는 W1에서 진입하며 실제 운행 분석은 데이터 검증 전 구현하지 않는다.

## 7. 레이아웃·색·접근성 토큰 제안

### 7.1 가변 창과 여백

- 앱 창 바깥 여백 24dp, 카드 안 여백 20–24dp, 관련 정보 간 8/12/16dp를 기본 token으로 삼는다.
- 주요 터치 타깃 사이 24dp를 우선한다. 좁은 폭에서는 타깃을 줄이지 말고 세로로 재배치한다.
- 헤더/하단 내비게이션/저장 영역은 minHeight를 사용한다. 글자 확대 때문에 필요한 높이까지 늘어나야 한다.
- system bar, cutout, IME inset을 동적으로 반영한다. OS GNB·공조 영역에 앱 버튼을 그리지 않는다.
- Google Android Auto의 0–600/600–930/930–1280/1280+dp 구간은 해당 템플릿 체계의 기준이다. 아래 CARITDA 구간과 혼합하지 않는다. [G13]

| 실제 앱 창 너비 | CARITDA 제안 동작 |
|---|---|
| 600dp 미만 | 단일 열. 목록→상세는 화면 이동. 증상 선택·행동 버튼은 세로/줄바꿈 |
| 600–839dp | 기본 단일 열, 충분한 경우 짧은 요약 카드만 2열 |
| 840dp 이상 | 높이·fontScale·최소 pane 폭이 충분할 때 목록/상세 2-pane 검토 |
| 좁은 폭 또는 150–200% 확대 | 탭/제목을 압축하지 말고 높이를 늘린다. 확장 3탭이 맞지 않으면 현재 섹션이 보이는 ‘메뉴’ 버튼과 세로 목록으로 대체 |
| 낮은 높이·키보드 열림 | 반복 설명을 접고 본문 스크롤을 확보. 핵심 저장/취소는 접근 가능하게 유지 |

이는 구현 출발점이지 Pleos의 강제 breakpoint가 아니다. 2-pane은 각 pane에 큰 글자와 76dp 타깃이 들어갈 때만 켠다.

### 7.2 색과 의미

| 상태 | 텍스트/형태 | 색의 역할 |
|---|---|---|
| 현재 선택 | 체크 + ‘선택됨’ + 테두리 | 청색/밝은 청색 강조 |
| 인계 미확인 | ‘읽음 확인 필요’ + 아이콘 | amber 보조. 고장 심각도 의미가 아님 |
| 사용자 해결 확인 | ‘사용자 해결 확인’ 라벨 | 중립적 상태 배지. 차량 정상 보증 아님 |
| 데이터 없음 | ‘미연동/미수집’ | 회색·중립. 0이나 정상으로 대체 금지 |
| 오래된 데이터 | ‘마지막 수신 … / 오래됨’ | amber + 시각 |
| 오류 | ‘불러오지 못함/저장 실패’ | 오류 라벨 + 재시도. 기존 데이터 보존 |
| OEM 경고 | 검증된 OEM 값·정의가 있을 때만 | 공식 심각도에 따라 사용. 사용자 증상에서 빨간 경고를 추론하지 않음 |

제안 팔레트는 OEM 실측 색이 아니다. 시스템 테마를 기본으로 밝은/어두운 테마를 제공하고, 색 조합별 대비를 검증한다.

- 밝은 배경 #F4F6F8, 카드 #FFFFFF, 본문 #17212B, 보조 #4E5D6C, 강조 #075BAA/흰 글자.
- 어두운 배경 #101820, 카드 #1C2936, 본문 #F0F4F8, 보조 #B7C4D1, 강조 #8CC8FF/짙은 글자 #062B49.

### 7.3 고령 사용자·focus 검수

- 이름·핵심 숫자·버튼은 실제 크기에서 읽히는지 확인한다. 최소 글자 하한만 맞추고 통과라고 하지 않는다.
- 모든 터치 영역·contentDescription·선택 상태를 검사한다. 동일 텍스트가 두 번 낭독되지 않도록 한다.
- 경고/오류/성공을 색이나 토스트 하나로 끝내지 않는다.
- 확대 시 말줄임으로 버튼의 의미가 바뀌면 안 된다. 카드 미리보기 말줄임과 저장 원문 보존은 별개다.
- 시스템 sans-serif와 한글 fallback을 우선한다. OEM 폰트 다운로드나 새 UI 프레임워크 전환은 최소 개편의 필수 조건이 아니다.

## 9. Codex 전달용 구현 요구사항

### 9.1 작업 경계

- 기존 프로젝트·Gradle·Android Studio/SDK 환경을 재사용한다. 새 프로젝트 생성이나 전면 재작성은 하지 않는다.
- 기존 model/data/domain/safety 구조를 먼저 읽고 UI와 필요한 운전자 데이터 모델만 점진적으로 수정한다.
- View 기반 구현을 유지해도 된다. Compose/Material/Car UI library 도입 자체를 목적 삼지 않는다.
- 기존 문제 기록·인계·조치·재발·상담 기능과 로컬 저장을 유지한다.
- ASIDE_RESEARCH.md, CARITDA_INTEGRATED_REVIEW.md 등 기존 조사 기록을 덮어쓰지 않는다.
- 이 문서의 조사 커밋은 소스를 바꾸지 않는다. **아래는 별도 후속 구현 작업의 요구사항**이다.

### 9.2 논리 상태와 데이터 원칙

- pendingDriverId와 confirmedDriverId를 구분한다. 카드 선택만으로 repository의 현재 운전자를 저장하지 않는다.
- 운전 시작 핸들러는 입력 허용 상태·후보 유효성·보관 여부를 재확인하고, 실패하면 확정하지 않는다.
- 최근 선택 복원과 이번 앱 이용의 기록 주체 확인을 구분한다. 구성 변경은 기존 확인을 보존한다.
- 인계 확인은 issue ID + revision + actor ID를 기준으로 중복 방지한다.
- 문제와 event의 원 작성자는 수정하지 않는다. 이름 변경·보관으로 이력 소유자가 바뀌지 않게 한다.
- 초안은 4.5.1에 따라 로컬 cache에 보존한다. dirty 초안을 둔 채 전환할 수 없으며, 저장 성공/명시적 취소/계속 작성의 결과를 구분한다. 구성 변경·정상 재실행 후에도 원 작성 주체로만 복원한다.
- UI가 임시로 성공 표시를 한 뒤 DB 실패를 숨기지 않는다. 쓰기 완료 후 성공을 표시한다.
- 기존 A/B 이전에 파괴적 schema upgrade를 사용하지 않는다. 스키마 확인·fixture·이전 전후 대조를 수행한다.
- 임의 차량 값, mock 정상 상태, 자동 경고·운전 점수·완료된 전송을 실제 기능처럼 표시하지 않는다.

### 9.3 화면·상태 요구

- M0 top-level은 홈/문제, 운전자 선택은 공통 진입점. W1–W6의 역할을 분리한다.
- 처음 등록은 이름/별명만. 기존 사람 선택 후 운전 시작으로 바로 홈에 도달한다.
- 모든 주요 화면에 loading/empty/error/restricted 상태를 정의한다. ‘빈 목록’과 ‘불러오기 실패’를 구분한다.
- Restricted/Unknown에서는 원인·가능한 다음 행동을 설명한다. 수동으로 ‘정차 확인됨’을 만드는 우회 스위치를 두지 않는다.
- 기록 source와 사용자가 표시한 해결 상태를 계속 노출한다.
- 요약에는 범위·시간대·외부 미전송을 명시한다. 기능 없는 공유 아이콘을 두지 않는다.
- 탐색 시 뒤로는 직전 맥락과 목록 위치를 가능한 범위에서 복원한다. 항상 홈으로만 튕기게 만들지 않는다.
- 테스트용 식별자는 의미 단위로 유지하거나 호환시킨다. 시각 문구 변경 때문에 기존 검증이 조용히 빠지지 않게 한다.

## 11. 아직 남은 확인과 최종 권고

- 이름 중복·당시 이름 snapshot·초안 보존과 전환 차단의 M0 정책은 4절로 고정한다. 기존 DB의 정확한 migration DDL과 앱 전용 cache 구현 수단은 실제 모델을 읽고 구현 전에 확정한다.
- 타깃 Pleos 창 크기·밀도·폰트 설정·rotary 유무·지역 UXR 정책은 실제 장비/에뮬레이터로 확인해야 한다.
- 공개 API 목록과 수신 성공은 다르다. blocked telltale·타이어 API를 화면 설계만으로 사용할 수 있게 되지는 않는다.
- 실제 앱 화면의 고령 사용자 가독성, 버튼 발견성, 운전자 오선택률, 정비 상담 효용은 미검증이다.
- Tesla 화면 원본은 재조회 403으로 미확보했다. Volvo PDF를 XC90 화면 증거로 혼용하지 않는다.

**권고:** 현재 강점인 로컬 문제 기록·인계·상담 요약을 유지하고, 이름 기반 기록 운전자와 명시적 시작·단순한 화면 구조부터 구현한다. 차량 UI답게 보이는 장식보다 ‘누가, 무엇을, 언제 기록했고 다음 사람이 무엇을 확인해야 하는지’가 먼저 읽히도록 한다.
