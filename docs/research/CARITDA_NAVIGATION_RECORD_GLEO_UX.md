## 0. 결론과 작업 경계

1. **C 권장:** 앱 내부 ‘홈’을 스크롤과 분리된 같은 위치에 두고, 공간이 충분할 때만 짧은 섹션 탭을 함께 제공한다. 고정 하단 3탭은 강제하지 않는다.
2. ‘이전’은 직전 맥락, ‘홈’은 CARITDA 첫 화면이다. 차량 OS의 전역 홈으로 앱 내부 홈을 대신하지 않는다.
3. 홈에서 **전체 문제 기록 / 내가 작성한 문제**를 구체적으로 보여준다. 목록 기본값은 모든 상태이며 검색·필터 조건을 드러낸다.
4. 편집은 사용자 작성 내용만, 삭제는 대상·복원 가능성·연결 이력 영향을 명시한다. 센서 원관측은 수정·삭제의 대상으로 묶지 않는다.
5. Gleo 문서상 **A(음성→앱 기능) 지원**, **B(앱에서 독립 상담 시작)는 미확인**, **C(선택 기록의 로컬 상담 내용 준비)는 자체 기능으로 설계 가능**이다. 결과 Callback을 새 대화/LLM API로 해석하지 않는다.
6. 저장 오류 수정과 실제 편집·삭제 구현은 다른 작업자의 범위다. 이번 조사에서는 앱·DB·설정·기존 문서를 수정하거나 빌드/실행하지 않는다.

표시 원칙: **확인 사실**은 읽은 코드·공식 자료의 내용, **설계 제안**은 CARITDA 적용안, **미검증 가정**은 실제 구현·사용자 시험이 필요한 효과다. 사용자 피드백은 조사 출발점이지 이번에 재현한 시험 결과가 아니다. CARITDA는 상표 검증 전 가칭이다.

### 2.1 OS 전역 홈과 CARITDA 홈

위 네 사례의 홈은 모두 **차량 전역 홈**이다. CARITDA 첫 화면으로 돌아오는 기능의 직접 사례가 아니다. 집 아이콘과 OS 바를 앱 안에 그대로 복제할 근거도 아니다.

Google의 AAOS 문서는 하드웨어/소프트웨어 뒤로 affordance가 필수라고 보장하지 않는다. OEM마다 시스템 바 위치와 정책도 다르다. 따라서 시스템 뒤로 또는 전역 홈이 CARITDA 탐색 문제를 해결할 것이라고 기대하지 않는다. [A1]

Google Car UI의 앱 헤더/앱 바는 제목·뒤로·탭·컨트롤을 다루며 좁은 구성에서는 다른 탐색 표현을 쓸 수 있다. 이는 앱 내부 탐색과 시스템 홈을 구분하는 근거이지 **고정 하단 3탭 의무**가 아니다. [A2] 앱 바의 좁은 구성 도해 [I2]와 기아 메뉴바 [I1]를 직접 열어 비교했다.

가져올 원칙: 예측 가능한 탈출구, 홈과 이전의 분리, 현재 위치 표현, 콘텐츠와 탐색의 분리. 가져오지 않을 것: OEM 아이콘/물리키 동작·독창적 배치·색 조합·픽셀 치수 복제. 네 사례의 실제 dp는 미확인이다.

### 3.1 권장 C의 구체 규칙

**앱 콘텐츠 영역 안의 최상단 탐색 바를 본문 ScrollView와 분리한다.** OS 상태/GNB/공조 영역을 덮지 않는다.

- 첫 위치의 글자 버튼 **‘홈’**은 주요 화면에서 같은 위치에 둔다. Home에서는 선택된 현재 위치로 표시하고 재누름은 무동작이다.
- 충분한 창에서는 같은 바에 **홈 / 기록 / 차량 정보**를 짧은 섹션 탐색으로 제공한다. 하단 배치가 필수는 아니다. 이번 권장 기본 배치는 상단이다.
- 좁은 창·큰 글씨에서는 **홈 / 메뉴**만 유지한다. 메뉴는 기록·차량 정보·사용법처럼 구체적 항목을 연다. 홈 자체는 메뉴 안에 숨기지 않는다.
- 600dp 등은 출발점일 뿐이다. 실제 글자·fontScale·높이·inset으로 세 항목이 최소 타깃을 유지하며 들어갈 때만 펼친다. 줄이지 못하면 보조 탭을 메뉴로 바꾼다.
- 현재 화면 제목과 **‘이전’** 또는 **‘원래 화면으로’**는 바 아래 첫 콘텐츠에 표시한다. 아이콘만 외우게 하지 않는다.
- 작성/수정에서는 보조 탭을 접고 홈·이전·저장/수정 취소의 목적을 명확하게 한다. 작은 창에서 제목·설명을 스크롤하더라도 홈 위치는 유지한다.
- 홈에 **전체 문제 기록 / 내가 작성한 문제 / 차량 정보 / 사용법**을 직접 제공한다. 메뉴를 기억하지 않아도 주요 기능을 찾게 한다.

이는 기존 하단 와이어프레임을 절대 규칙으로 해석하지 않고 이번 사용자 피드백을 반영한 보완안이다. 처음 보는 사용자가 더 잘 이해한다는 효과는 별도 시험해야 한다.

### 3.2 홈·이전·닫기와 이력

| 행동 | 의미·결과 |
|---|---|
| 홈 | CARITDA HOME으로 직접 이동. 중첩 화면 이력을 정리해 홈에서 이전 상세로 되튀지 않음. 운전자·검색 상태·DB는 초기화하지 않음 |
| 이전 | 직전 화면의 필터·검색어·목록 위치로 복귀. 홈으로 위장하지 않음 |
| 사용법의 원래 화면으로 | 도움말을 연 화면으로 복귀, 작성 중 초안과 커서/focus 맥락 복원 |
| 앱/OS 전역 Home | 앱 밖 시스템 이동. 명시적 수정 취소/기록 삭제가 아님. lifecycle 초안 보존 적용 |
| 삭제 확인의 취소·시스템 뒤로 | 확인 창만 닫고 동일 상세로 복귀. 아무 삭제도 하지 않음 |

앱 내부 홈을 누르려고 시스템 HOME intent를 실행하거나 앱을 종료하지 않는다. 내부 tag/테스트 ID도 실제 ‘홈’과 ‘이전’을 구분해 자동 검사가 잘못된 성공을 내지 않게 한다.

### 3.3 수정 중 홈 이동

1. 미변경 상태면 바로 홈.
2. 변경된 내용은 **확정 기록과 다른 수정 초안**으로 보존한다. 보존 성공 후 홈으로 이동하고 ‘수정 중인 기록이 있어요 / 계속 수정’을 제공한다. 원문을 저장한 것으로 표시하지 않는다.
3. 초안 보존 실패면 원래 화면에 남기고 ‘계속 수정 / 수정 내용 버리고 홈’을 제공한다. 버리기는 명시적으로 확인한다. 실패했는데 보존됐다고 말하지 않는다.
4. `저장`만 확정 본문을 갱신한다. `수정 취소`만 해당 수정 초안을 폐기한다. 홈·이전·전화 수신·OS 전환을 일률 discard로 처리하지 않는다. [U3]
5. 한 개 초안 제약 등 실제 저장 모델과 맞춘다. 기존 새 기록/조치 초안을 덮어써서 편집을 시작하지 않는다.

일반 화면의 홈은 1회 터치 목표다. **삭제 확인 같은 modal에서는 취소 후 홈, 2회**다. 초안 보존 실패의 보호 선택도 별도 횟수로 기록한다. 위 수치는 가설적 설계 경로이며 실제 기기 완료 시간을 측정한 결과가 아니다.

## 4. 전체/내 기록 찾기

### 4.1 기본 목록

- 홈의 **전체 문제 기록**은 관리 중·완료를 모두 포함하고 휴지통은 제외한다. 이전 필터 때문에 조용히 일부만 보여주지 않는다.
- **내가 작성한 문제**는 확정된 기록 이름의 stable ID로 필터링한다. 표시 이름 문자열로 비교하지 않는다. 이름을 바꾸거나 예전 snapshot 이름이 남아도 같은 ID의 기록을 찾는다.
- 이름 미확정이면 이름 선택 후 원래 목표인 ‘내가 작성한 문제’로 돌아간다. 이름 선택은 본인 인증이 아니라는 한계를 안내한다.
- 목록 기본 정렬 제안은 **최근 등록순**, 동률은 stable ID다. 수정만으로 발견일·등록일을 바꾸지 않는다. 다른 정렬을 제공하면 현재 조건을 표시한다.
- 카드에 증상·짧은 본문·등록자·발견일·상태·수정됨을 표시한다. 미리보기 말줄임과 전체 원문 저장은 별개다.

### 4.2 검색과 필터

- 검색 진입을 목록에 **검색**이라고 노출하고 ‘단어나 상황으로 찾기’를 안내한다.
- 검색 대상은 전체 본문·메모·카테고리다. 카드의 첫 100자만 검색하지 않는다. 검색어는 로컬 처리하며 Gleo/서버에 보내지 않는다.
- 빠른 작성자 범위 **전체 / 내가 작성**와 별도 **필터**를 제공한다. 필터는 우선 상태(모두/관리 중/완료), 증상 종류 정도로 제한한다.
- 적용한 조건·결과 수·**조건 지우기**를 보여준다. ‘검색 결과 없음’과 ‘차량 기록 자체가 없음’을 구분한다. [U2]
- 카드→상세→이전이면 검색어·필터·스크롤 위치를 유지한다. 수정 후 검색어와 달라져 목록에서 빠지면 ‘수정한 내용이 현재 조건과 달라요 / 전체 기록 보기’를 안내한다.
- 읽지 않은 인계는 홈의 별도 바로가기로 제공한다. ‘전체 기록’의 의미를 몰래 ‘읽지 않은 것만’으로 바꾸지 않는다.

## 5. 사용자 기록 편집: 권한·취소·이력

### 5.1 권한은 UX 정책이며 인증이 아니다

| 행위 | 권장 M0 정책 |
|---|---|
| 같은 앱의 문제 읽기·로컬 상담 요약 | 기존 공유 기록 범위 유지 |
| 본문 수정·삭제 | 확정된 기록 이름 ID가 원 작성자 ID와 같을 때 제공. 저장 직전 서비스/저장 계층에서도 재검사 |
| 타인 기록 | 원문 수정/삭제 대신 기존 읽음·자기 조치 메모 등 허용된 행동 유지 |
| 작성자 변경 | 편집 필드에서 제공하지 않음. 원 작성자 ID/당시 이름/최초 시각 불변 |
| 센서 원관측 | 사용자 본문 편집/삭제와 별개. 값·단위·출처·수신 시각을 바꾸지 않음 |

**이름만 선택하는 로컬 프로필은 보안 인증이 아니다.** 다른 이름을 고를 수 있는 공유 환경에서 ‘본인만 접근 가능’이라고 광고하지 않는다. 신뢰할 수 있는 개인 권한 경계가 필요하면 별도 인증/접근 통제 검증이 필요하다. [U4]

일반 안내 예: ‘이 기록을 남긴 이름으로 선택한 경우 수정·삭제할 수 있어요.’ 사용법에는 ‘이름 선택은 잠금이나 본인 인증 기능이 아니에요’를 명시한다.

### 5.2 편집 흐름

~~~text
문제 상세 → [수정]
  → 카테고리 / 본문 / 추가 메모 편집
  → [저장] → 서비스의 작성자·안전·기준 버전 재확인
      성공: 같은 기록 ID의 상세 + ‘수정했어요’
      실패: 편집값 유지 + 오류/재시도
  → [수정 취소] → 변경 있으면 확인 → 기존 상세
  → [홈] → 수정 초안 보존 후 홈, 원문은 미변경
~~~

- 이번 최소 편집 범위는 카테고리·본문·추가 메모다. 원 작성자·최초 등록/발견 시각·센서값·다른 사람의 조치 원문은 편집하지 않는다.
- 기존 상황 1,000자/메모 2,000자 등 실제 validation을 확인해 유지한다. 빈 본문은 입력 옆에서 수정 방법을 알려준다.
- 저장 중 반복 탭 방지, 완료 후에만 성공 표시. 중복 저장 요청은 동일 수정 요청으로 식별해 중복 이벤트/가짜 실패가 생기지 않게 한다.
- 변경 없는 저장은 불필요한 새 이력을 만들지 않는 것을 기본으로 한다.
- 삭제·다른 수정·작성자/안전 상태 변화가 발생했으면 조용히 덮어쓰지 않는다. 기준 버전 충돌을 알리고 편집 초안은 유지한다.

### 5.3 수정·읽음·재발 차수를 분리

현재 issue.revision은 재발과 읽음 확인에 사용된다. 새 편집을 단순히 ‘재발 +1’로 만들지 않는다. 다음은 **논리적 요구사항**이며 기존 Codex가 추가하는 스키마와 매핑해야 한다.

- 기록 ID는 유지한다. 수정마다 본문 버전(contentVersion 등)을 식별하고 수정자/수정 시각/바뀐 필드 이력을 남긴다.
- 재발 차수와 본문 버전은 다른 의미다. 예: **재발 2차의 본문 수정 3판**. 이름은 제안이며 기존 열을 임의 재해석하지 않는다.
- 읽음은 당시 본문 버전에 연결한다. 본문/카테고리/공유 메모가 바뀌면 다른 운전자에게 ‘내용이 수정됐어요 / 다시 읽기’를 표시한다. 과거 읽음을 지우거나 새 판을 자동 읽음 처리하지 않는다.
- 조치·상태 이력은 당시 내용 버전을 참조한다. 예전 조치가 새 본문에 대한 판단인 것처럼 표시하지 않는다.
- 수정은 해결/재발 상태를 자동 변경하지 않는다. 상태 변경은 별도 명시 동작이다.
- 이전 상담 요약·향후 AI 답변은 참조 기록 ID/내용 버전에 연결한다. 원문이 바뀌면 ‘작성 후 내용이 수정됐어요’를 표시하고 최신 조언처럼 재사용하지 않는다.
- snapshot/초기 A/B 매핑·읽음 중복 방지·원래 이력 관계를 보존한다. 구체 migration은 실제 최신 모델 검토 후 비파괴적으로 설계한다. [U5]

## 6. 삭제 UX와 삭제의 정확한 의미

### 6.1 기본 제안: 휴지통 이동 + 복원

상세에는 숨은 제스처가 아닌 글자 버튼 **‘수정’ / ‘삭제’**를 제공하되, 삭제는 강조 주 CTA와 떨어진 보조/위험 영역에 둔다. 빨간색만으로 구별하지 않는다.

삭제 클릭 후:

- 제목: **‘이 기록을 휴지통으로 옮길까요?’**
- 대상: 증상·짧은 본문·등록자·발견일. 기록 ID는 내부로 유지한다.
- 설명: **‘일반 목록에서 보이지 않게 되며 휴지통에서 되돌릴 수 있어요. 차량에서 받은 값은 그대로 남아요.’**
- 버튼: **‘취소’ / ‘휴지통으로 이동’**. 취소가 안전한 기본 선택이며 파괴 행동에 초기 focus를 주지 않는다.
- 연결된 조치/읽음이 있으면 이 기록의 이력도 일반 화면에서 함께 숨겨진다는 사실을 덧붙인다.

확정 성공 후 현재 목록·필터로 복귀하고 **‘휴지통으로 옮겼어요 / 실행 취소 / 휴지통 보기’**를 보여준다. 시간 제한 toast만 복원 경로로 삼지 않는다. 기록 화면의 휴지통 진입도 제공한다. [U1]

### 6.2 휴지통·복원·영구삭제는 서로 다르다

| 정책 | 실제 의미·표시 |
|---|---|
| 목록 숨김/휴지통 | 원문은 남아 있다. 일반 검색·카운트·인계 큐·새 상담 payload에서 제외하고 관계를 보존 |
| 복원 | 기존 ID/상태/버전/이력으로 복원. 새 문제를 생성하거나 새 읽음으로 처리하지 않음 |
| 기본 보관 | 이 제안에서는 자동 보관기한/자동 영구삭제를 두지 않음. ‘직접 완전히 지울 때까지 보관돼요’를 명시. 법정 기간을 추정하지 않음 |
| 영구삭제 | 별도 휴지통 화면에서 명시적 확인. ‘이 앱에서는 되돌릴 수 없어요’와 지워지는 원문/수정본/연결 이력·로컬 파생 상담 내용의 범위를 설명 |

영구삭제를 구현하지 않았다면 있는 것처럼 노출하거나 ‘완전히 지웠어요’라고 쓰지 않는다. 휴지통만 제공하는 초기 버전은 **복원 가능한 이동임을 명시**하고, 개인 내용의 완전 삭제 요구를 처리할 방법은 배포 전에 별도 확정한다.

영구삭제 설계 시 원문과 수정 snapshot·연결 초안·로컬 파생 요약의 잔존을 점검하고, 감사에 필요한 최소 삭제 메타데이터와 본문 복제를 구분한다. 독립 센서 관측은 남기고 사용자 기록과의 참조만 적절히 해제한다. 외부에 이미 전달한 사본·백업·SQLite 저장장치의 물리적 삭제까지 앱의 행 삭제로 보장하지 않는다. [U5]

### 6.3 실패·동시성·참조

- 확인 창을 열었다고 삭제하지 않는다. 취소·뒤로·창 밖 이동·OS Home은 삭제 확정이 아니다.
- 확정 직전에 작성자·기준 버전·UXR·현재 존재 여부를 재검사한다. 중복 탭은 한 번의 이동으로 처리한다.
- 실패하면 상세와 원문을 유지하고 성공 문구/카운트 감소를 먼저 보여주지 않는다.
- 삭제된 기록을 오래 열린 상세/편집/상담에서 참조하면 ‘삭제된 기록이에요’를 보여주고 저장·전송을 중단한다. 비슷한 다른 기록을 대신 선택하지 않는다.
- 연결된 다른 사람의 조치가 있는 경우 영향을 확인 창에 알린다. 삭제를 과거 조치를 조용히 고쳐 쓰는 기능으로 구현하지 않는다.
- 삭제 후 목록이 비어도 ‘조건에 맞는 기록 없음’과 ‘전체 기록 없음’은 구분한다. 복원 후 원래 위치/정렬 규칙을 적용한다.

이 기본안은 복원성을 높이는 **설계 제안**이다. Codex가 별도로 구현하는 삭제가 영구삭제라면 위 휴지통 문구를 그대로 적용하지 말고 실제 복원 가능성과 범위를 맞춰 재검토한다.

## 7. Gleo 공식 Interface 검증

지정한 Core Concepts [G1], App Schema [G2], Callback Schema [G3], Deliver Schema [G4]를 모두 확인하고 응답 전송 예제 [G5]를 보조 확인했다. 이번 작업에서 schema 제출·계정 신청·권한 부여·SDK 연동·실행은 하지 않았다.

### 7.1 지원 방향

| 구분 | 판정 | 실제 근거와 한계 |
|---|---|---|
| **A. Gleo 음성 → CARITDA 기록 기능** | Interface 방향은 지원, 실제 앱 적용은 조건부 | Gleo Action이 앱을 호출하고 Callback으로 응답을 받음. Intent 수신·schema·승인·인증·실행 검증 필요 |
| **B. 앱 UI 선택 기록 → 독립 Gleo 상담 시작** | **미확인, 현재 기능으로 약속하지 않음** | Callback은 앞서 호출된 function의 결과 회신. 임의 시점의 새 대화/일반 추론 API 근거가 아님 |
| **B의 제한된 변형** | 기존 Action 안의 결과 회신은 조건부 검토 | Gleo가 먼저 호출한 작업의 선택 결과를 반환하는 경우. 7초 취소·동의·현재 화면·응답 schema 검증 필요 |
| **C. 선택 기록의 로컬 상담 내용 준비** | 자체 앱 기능으로 설계 가능, 미구현 | 기존 기록을 바탕으로 로컬 요약/질문 목록을 구성. Gleo 전달/답변이 아니며 연동 완료라고 부르지 않음 |

공식 흐름은 다음이다.

~~~text
사용자 음성 → Gleo가 function 선택 → Android Intent로 앱 호출
→ 앱이 해당 동작 처리 → Callback 결과 → Gleo 최종 응답

이것은 아래 흐름의 증거가 아님:
임의 앱 버튼 → Gleo 새 대화/LLM 추론 요청 → 자유 상담 답변 수신
~~~

### 7.2 실수하기 쉬운 공식 세부

- Core Concepts는 Gleo가 Action으로 앱을 호출하고 Callback으로 앱 응답을 받는다고 명시한다. [G1]
- actionCalls는 음성으로 호출할 function 목록이며 **최대 3개**다. 문서상 activity는 startActivity, service는 sendBroadcast 경로로 설명된다. service라는 라벨을 Android Service 직접 시작으로 바꿔 읽지 않는다. [G2]
- Gleo가 모든 필수 parameter를 채운다고 보장하지 않는다. 누락/잘못된 기록 식별자를 검증하고 사용자의 다른 기록을 추정 반환하지 않는다. [G2]
- Callback의 functionName은 호출된 App Schema function과 일치해야 한다. data는 JSON 객체 배열을 문자열로 나타내는 필드다. 정확한 직렬화·허용 schema를 따른다. [G3]
- 문서는 **7초 후 Action 취소**를 명시한다. 사용자가 오래 선택/동의/상담하는 동안 같은 호출을 무한 대기시키지 않는다. asking은 추가 정보/확인 상태이지 영구 세션·새 대화 API가 아니다. [G3]
- 예제의 APP_ACTION_RESPONSE broadcast와 sendGleoBroadcast라는 예제 함수는 **응답 전송** 근거다. sendGleoBroadcast를 SDK 제공 새 추론 API라고 부르지 않는다. [G5]
- silent/beep 등은 출력 방식이지 LLM 상담 기능이 아니다. 일반 LLM SDK의 추론 호출 가능성과 Gleo Interface를 혼동하지 않는다.

### 7.3 등록·승인·배포·실행은 각각 별개

[G4]는 assets/schema.json, App Schema 검토/승인 후 통합 활성화, AndroidManifest의 action filter를 설명한다. 부팅 스캔 설명도 있다. 그러나 다음은 별도 확인 대상이다.

- CARITDA가 사용할 구체 SDK/버전/배포물, 파트너 자격·전달 채널·계약.
- 호출자 인증·manifest permission·broadcast 보호와 개인 기록을 반환할 권한.
- CARITDA 업데이트 뒤 재스캔/갱신 조건과 실제 대상 이미지 동작.
- schema 승인과 앱 마켓 배포 심사의 차이.
- 설치 성공, 음성 인식, Action 수신, Callback 성공, 최종 발화와 7초 취소의 실제 실행 결과.

공식 문서에 없는 API명·Gleo deep link·clipboard 대화 시작·권한 이름을 만들어 Codex에 넘기지 않는다.

## 8. 선택 기록 상담: 가능한 대안과 보류 흐름

### 8.1 지금 권장할 C 흐름

문제 상세의 기본 버튼은 **‘이 기록으로 상담 준비’**다. 아직 작동하지 않는 ‘Gleo에게 보내기’를 주 버튼처럼 두지 않는다.

~~~text
문제 상세 1건 → [이 기록으로 상담 준비]
→ 선택 기록의 로컬 미리보기
  현재 버전은 Gleo에 바로 보내 답변받는 기능을 제공하지 않음
→ [상담 내용 만들기] (로컬 템플릿)
→ 증상/언제/사용자 조치 + 추가로 설명할 정보 + 정비 질문
→ [원래 기록으로] / [홈]
~~~

이 대안은 향후 앱 기능 제안이며 이번에 구현하지 않았다. 자동 AI 답변이 아니다. 기존 선택 문제 상담 요약을 재사용할 수 있으나 전체 기록을 끼워 넣지 않는다.

**예시 선택 기록:** ‘가속할 때 앞쪽에서 소음이 발생함’

**준비할 내용 예시:**
- 남긴 증상: 가속할 때 앞쪽에서 소음이 발생함.
- 추가로 설명할 정보: 처음 느낀 때, 반복 여부, 소리를 느낀 위치, 당시 화면에 표시가 있었는지.
- 정비할 때 물어볼 질문: ‘이 증상과 함께 어떤 정보를 설명하면 점검에 도움이 될까요?’ / ‘안전하게 확인할 점검 절차는 무엇인가요?’
- 안내: ‘고장 원인이나 운행 가능 여부를 판단한 답이 아니에요. 확인하려고 일부러 급가속하거나 증상을 재현하지 마세요.’

복사/공유는 실제 AAOS 지원과 사용자가 고른 전달 경로를 검증한 경우에만 후속 제공한다. 복사했다고 Gleo에 전달됐다고 말하지 않는다. 기본 C는 앱 내부 조회이며 외부 전송이 없다.

### 8.2 A의 현실적인 최소 통합 후보

공식 승인 후 **음성으로 CARITDA 기록 화면을 여는 읽기 중심 Action**부터 검토한다. 이는 제안된 기능이지 이미 등록된 function/API 이름이 아니다.

- 호출 parameter를 검증하고 로컬 기록 화면으로 연결한다. 음성만으로 운전자 변경·편집·삭제·해결 확인을 실행하지 않는다.
- 최초에는 개인 본문을 Callback으로 반환하지 않고 필요한 최소 실행 상태만 응답하는 범위를 우선한다.
- 개인 내용을 반환하려면 호출자 검증·공유 권한·동의·발화 노출·응답 지연을 별도 확인한다. 한 사람의 이름 선택을 보안 인증으로 간주하지 않는다.
- 동의가 없으면 장시간 확인 창을 기다리며 7초를 넘기기보다 민감하지 않은 보류 결과를 공식 schema에 맞춰 처리하고 정차 후 앱 확인을 안내한다. 정확한 상태 필드는 승인된 schema 확인 후 정한다.
- Gleo 최종 응답이 만들어진다고 자동차 증상 전문 상담의 범위·품질·안전성이 검증된 것은 아니다.

### 8.3 B를 활성화하기 전 필요한 검증

1. 앱 UI에서 독립 상담을 시작하는 공식 API/지원 경로가 실제 존재하는지.
2. 선택 1건과 버전을 지정해 결과를 받을 상관관계·취소·중복·시간 제한.
3. 동의 화면: **어떤 기록·어떤 항목·어디로·왜 전달되는지**, 알려진 보관/처리 정책, 취소.
4. 전달 범위: 기본은 선택 증상·필요한 상황. 메모는 기본 제외하고 선택 동의. 이름·연락처·VIN·정밀 위치·SDK 세션·전체 기록은 기본 제외.
5. 타인이 작성한 기록의 외부 전달 권한과 실제 본인/동의 확인. 이 정책이 불명확하면 외부 전달을 막는다.
6. 전송 직전 원문 버전·삭제 여부·선택 기록 ID를 다시 확인하고, 바뀌었으면 미리보기를 갱신해 다시 동의받는다.
7. AI 결과는 원문·센서·상태를 자동 수정하지 않는다. 고장 원인·운행 가능 여부를 확정하거나 자동 정비 접수를 하지 않는다.
8. 기록 텍스트와 AI 답변은 자료다. 그 안의 문장을 앱 명령으로 실행하거나 삭제/전송 권한으로 사용하지 않는다.

조건이 확인되기 전 B는 **보류**다. 단순 LLM SDK 추가나 응답 broadcast 전송으로 완료 처리하지 않는다.

## 9. 8개 필수 화면의 한국어 와이어프레임

모든 예시는 설계용 가상 내용이다. 공통 상단 바는 앱 창 안의 고정 영역이다. 아래 [홈]은 차량 전역 홈이 아니다.

### W1. 앱 홈

~~~text
[홈 선택됨] [메뉴]               (넓으면 기록/차량 정보)
홈
기록 이름: 민수                  [변경]
지금은 차량 이상을 자동으로 찾지는 않아요.

[전체 문제 기록]                 → W2
[내가 작성한 문제]               → W3
[문제 남기기]                    → 기존 새 기록
[차량 정보]                      → 기존 차량 정보
[사용법]                         → W8
수정 중인 기록이 있어요          [계속 수정] → W5
~~~

홈 재누름은 무동작. 이름 변경은 기존 초안 규칙 유지. 작은 화면은 단일 열이고 홈 바만 고정한다. 긴 도움·센서 로그를 여기에 펼치지 않는다.

### W2. 전체 문제 기록

~~~text
[홈] [메뉴]
전체 문제 기록
[전체 선택됨] [내가 작성]         → W3
[검색: 단어나 상황으로 찾기]
[필터]  모든 상태 · 증상 전체     [조건 지우기]
결과 8건 · 최근 등록순

소음 · 가속할 때 앞쪽에서 소리
등록 민수 · 발견 날짜 · 관리 중
[내용 보기]                     → W4
[휴지통]                        → 보조 복원 화면
~~~

홈은 고정 바 1회. 이전은 직전 맥락. 필터 결과 0이면 ‘조건에 맞는 기록이 없어요 / 조건 지우기’. 실제 전체가 비었을 때만 최초 빈 상태 안내. 작은 화면/확대에서는 범위·검색·필터를 세로로 배치하며 홈을 숨기지 않는다.

### W3. 내가 작성한 문제

~~~text
[홈] [메뉴]
내가 작성한 문제
선택한 기록 이름: 민수
[전체] [내가 작성 선택됨]
[검색] [필터]
내 기록 3건
소음 · 가속할 때 앞쪽에서 소리   [내용 보기] → W4
~~~

ID 기준 필터이며 등록 당시 이름이 달라도 같은 작성자 ID를 찾는다. 다른 이름으로 전환하면 검색 범위 설명도 갱신한다. 작은 화면은 선택 범위를 줄바꿈하고 ‘내 기록’이 인증 보호 영역처럼 보이지 않게 도움을 제공한다. 홈 1회.

### W4. 문제 상세

~~~text
[홈] [메뉴]
[이전: 기록 목록]                → W2/W3의 원래 조건
문제 내용
소음 / 가속할 때 앞쪽에서 소음이 발생함
작성 민수 · 발견일 · 등록일 · 수정일
직접 남긴 기록 · 관리 중

[수정]                          → W5 (작성자 정책 충족)
[이 기록으로 상담 준비]          → W7
[점검하거나 한 일] [다시 발생했어요]
읽음/조치/수정 이력

[삭제]                          → W6 (작성자 정책 충족)
~~~

타인 원문이면 수정/삭제 대신 작성자 안내, 기존 읽음/자기 조치는 유지한다. 삭제는 저장/상담과 떨어뜨린다. 작은 화면은 행동을 한 열로 배치하고 현재 기록의 제목/작성자를 확인 후 동작한다. 홈 1회.

### W5. 기록 수정

~~~text
[홈]
[이전: 문제 상세]                → W4 (초안 보존)
기록 수정
작성자 민수 · 원래 등록일 (수정 불가)
카테고리 [소음/진동/경고등/기타]
본문 [가속할 때 앞쪽에서 소음이 발생함]
추가 메모 [선택]

[저장]                          → 성공 후 같은 W4
[수정 취소]                     → 변경 있으면 확인 후 W4
~~~

홈 1회는 수정 초안만 보존한다. 초안 실패 시 이동을 멈춘다. 저장 실패/버전 충돌은 입력 옆 안내와 재시도이며 성공으로 위장하지 않는다. 작은 창·IME에서는 저장을 접근 가능한 영역에 두고 본문을 스크롤한다. 고정 하단 저장 영역이 OS/GNB/키보드를 덮어서는 안 된다.

### W6. 기록 삭제 확인

~~~text
이 기록을 휴지통으로 옮길까요?
소음 / 가속할 때 앞쪽에서 소리
등록 민수 · 발견 날짜

일반 목록에서 숨겨지고 휴지통에서 되돌릴 수 있어요.
차량에서 받은 값은 그대로 남아요.
[취소]                          → W4, 원문 불변
[휴지통으로 이동]               → 성공 후 W2/W3
~~~

modal 중 배경 홈은 누르지 않는다. 홈으로 가려면 취소→홈 2회. 시스템 뒤로도 취소다. 작은 화면에서는 대상·영향을 스크롤할 수 있고 두 버튼은 세로 배치한다. 삭제/영구삭제 종류와 문구가 실제 구현과 일치해야 한다.

### W7. 선택 문제 상담 진입/대안

~~~text
[홈]
[원래 기록으로]                  → W4
선택한 기록 상담
소음 / 가속할 때 앞쪽에서 소음이 발생함

이 버전에서는 Gleo에 바로 보내 답변받는 기능을 제공하지 않아요.
[상담 내용 만들기]               → 로컬 요약·질문 (외부 전송 없음)

내가 남긴 증상 / 추가로 설명할 정보 / 정비 질문
AI가 진단한 답이 아니에요.
~~~

홈 1회, 선택 1건·본문 버전을 유지한다. 작은 화면은 한 부분씩 읽게 하고 전송되지 않았다는 사실을 숨기지 않는다. B가 실제 지원될 때만 명확한 미리보기·동의·취소/실패·답변 구분 화면을 별도 추가한다.

### W8. 사용법

~~~text
[홈] [메뉴]
사용법
[원래 화면으로]                  → 열기 전 화면·초안
[홈과 이전은 어떻게 다른가요?]
[내가 쓴 기록 찾기]
[수정하고 저장하기]
[삭제·휴지통에서 되돌리기]
[선택한 기록으로 상담 준비하기]
[현재 자동 확인/Gleo의 범위]
~~~

각 항목은 해당 기능이 실제 구현된 버전만 설명한다. 홈은 1회, 원래 화면 복귀는 별도 명시 행동이다. 작은 화면에서 사용법 목차도 스크롤되지만 홈 바는 유지한다. 도움말을 닫아도 저장·삭제·Gleo 전송을 실행하지 않는다.

## 10. 안전·터치·가독성

- 홈·검색·편집·삭제·동의·긴 상담은 현재 정차용 Activity와 기존 UXR 범위 안에서만 제공한다. 홈 버튼이 고정됐다고 주행 중 접근을 허용하지 않는다. [P1] [P2]
- UNKNOWN/RESTRICTED에서는 쓰기·외부 전송·동의를 우회하지 않는다. OS가 앱을 가리면 앱 내부 홈을 계속 볼 수 있다고 보장하지 않는다. requiresDO=false는 기어 P 증명이 아니다. [R9]
- 새 탐색 제어도 기존 76dp 최소 터치 영역·24sp 중심 글자를 **프로젝트 목표**로 유지한다. 모든 Pleos 정차 앱의 동일 법적 의무라고 주장하지 않는다. [R1] [R2]
- 실제 앱 window의 dp·system/IME inset을 사용한다. 320/480/600/840/1024dp, 100/130/150/200% fontScale와 낮은 높이를 검사한다.
- 작은 높이에서 제목/보조 설명은 스크롤하고 보조 탭을 접는다. 홈과 핵심 타깃을 작게 줄이거나 의미를 말줄임해 넣지 않는다.
- 홈/이전/선택/삭제를 색·집 그림 하나로만 전달하지 않는다. 텍스트 라벨, 명확한 focus, 읽기 순서·동작 후 focus 복귀를 검수한다.
- 물리/시스템 뒤로가 없을 수 있으므로 앱 안에 이전·취소·닫기 경로를 제공한다. 반대로 OS Home/앱 중단을 임의 삭제로 처리하지 않는다. [A1] [U3]
- 음성이라고 자동으로 안전한 것은 아니다. 민감 기록 낭독, 다단계 확인, 장시간 대화는 대상 차량 정책과 실제 주의부담을 검증해야 한다.

## 11. Codex 전달 요구사항

### 11.1 동시 작업과 선행 조건

- 이 문서의 커밋은 연구 파일만 추가한다. 저장 오류 수정·편집삭제 구현에 직접 손대지 않는다.
- 후속 구현 전 최신 main의 서비스/스키마/원자성/수정·삭제 정책을 다시 읽는다. 기존 작업을 이전 버전으로 덮어쓰지 않는다.
- 사용자 저장 오류의 재현→실제 저장/재조회/재시작 보존 검증을 먼저 수행한다. 저장이 안 되는 상태에서 화면 이동 성공만 인수하지 않는다.
- 별도 개발 중인 편집/삭제 API가 있으면 이 문서의 논리 요구와 매핑하고, 서로 다른 삭제 의미/버전 모델을 두 개 만들지 않는다.

### 11.2 구현 핵심

1. goHome, goBack, closeHelp를 다른 의미로 분리한다. 홈은 내부 HOME으로 이동하며 도움말/중첩 이력을 정리하되 영구 데이터·기록 주체는 유지한다.
2. 최상단 홈 바는 본문 스크롤과 분리한다. 좁은 창은 홈/메뉴, 충분한 창만 보조 섹션 탭을 제공한다.
3. 전체/내가 작성 검색 상태를 명시적으로 관리하고 상세 복귀 시 복원한다. 조회 0과 오류·빈 DB를 구분한다.
4. 편집은 같은 기록 ID, 원 작성자/시각 유지, 별도 수정 버전/초안·낙관적 충돌 검사·중복 저장 방지를 갖춘다.
5. 삭제는 실제 정책을 UI와 일치시킨다. 휴지통이면 모든 정상 쿼리/인계/새 상담에서 제외하고 지속적인 복원 경로를 제공한다.
6. 센서 원관측을 사용자 편집·삭제·AI 답변의 변경 대상으로 연결하지 않는다.
7. Gleo A는 승인된 읽기 중심 범위부터 실험하고, B는 공식 지원·개인정보·호출자 검증 전 활성화하지 않는다. C는 로컬 내용 준비라고 표시한다.
8. 상담은 선택 1건·내용 버전·전송 범위에 묶는다. 전체 이력 자동 첨부·무동의 외부 전달·AI 자동 확정 동작을 금지한다.

## 12. 사람 대상 사용성 검증 계획

자동 UI 클릭 검사는 컴포넌트·저장·이력·회귀를, 사람 시험은 발견성·의미 이해·실수를 본다. 자동 assertion 수를 일반 운전자 성공률로 환산하지 않는다.

### 12.1 과제와 관찰

경로를 알려주지 않고 과제 목적만 제시한다. 안전하게 정차한 시험 환경/에뮬레이터에서 가상 기록을 사용한다.

| 과제 | 성공 기준 | 오해·오작동 관찰 |
|---|---|---|
| 현재 화면에서 앱 홈으로 돌아가기 | CARITDA HOME 도달, 일반 화면 1회 터치 목표 | OS 홈/앱 종료, 메뉴 탐색, ‘이전’ 반복, 스크롤 찾기 |
| 자신이 작성한 문제 찾기 | 지정 기록 이름 ID의 가상 증상 한 건을 선택 | 다른 작성자/상태 필터/검색 결과를 전체 부재로 오해 |
| 문제 수정 | 지정 필드만 저장, 같은 기록 상세 확인 | 새 문제 생성, 원문 아닌 초안만 저장한 것으로 오해 |
| 삭제 확인 취소 | 원문 보존·같은 상세 복귀 | 창 열림/배경 터치/홈을 삭제 확정으로 오해 |
| 필요한 기록 삭제 | 지정 한 건만 실제 정책대로 제거, 복원 경로 설명 | 다른 사람/다른 기록 삭제, 휴지통을 완전삭제로 오해 |
| 선택 기록 AI 가능 여부 | 현 버전의 직접 Gleo 미지원과 로컬 C를 설명 | 상담 내용 준비를 AI 답변/실제 전송/고장 진단으로 오해 |
| 사용법 후 원래 화면으로 | 열기 전 화면·필터·초안으로 복귀 | 홈과 닫기의 혼동, 작성 내용 유실, 자동 저장 추정 |

### 12.2 측정과 진행

- 형성 평가 예: 자동차 비전공 운전자 8명, 다양한 연령·디지털 숙련·공동 차량 경험 포함. 고령자/저시력 접근성을 별도로 관찰하고 나이·성별로 능력을 단정하지 않는다.
- 독립 성공/부분/실패, 첫 올바른 행동 시간·전체 시간, 탭/스크롤·잘못 누름·이전 반복·되돌림·관찰자 구제·포기·기능 의미 설명을 기록한다.
- 성공률은 독립 성공 수/실행 가능한 과제 수로 제시하고 차단·미구현 과제는 별도 보고한다. B 미지원 상태에서 실제 Gleo 답변을 못 받았다고 사람의 실패로 세지 않는다.
- 홈 1회 목표와 modal 2회 예외, 초안 보존 실패 보호 선택을 구분해 계산한다. 입력 문자 수·스크롤은 터치 횟수와 따로 보고한다.
- ‘내 기록만 보호된다’, ‘삭제하면 센서값도 지워진다’, ‘준비 버튼이면 Gleo로 보냈다’ 같은 중대 오해는 문구/구조 수정 후 새 참여자로 재검증한다.
- 참가자가 위험한 증상을 실제로 재현하거나 주행 중 화면을 조작하게 하지 않는다. 정차 시험으로 주행 안전 인증을 주장하지 않는다.
- 작은 표본 결과는 기술 통계다. 같은 사람이 학습 후 반복한 개선을 순수 A/B/C 우월성으로 세지 않는다. 버전·기기·가상 데이터·실패/구제 기준을 함께 기록한다.

## 13. 저작권·구현 범위·미확인

- 제조사/Google 화면은 원칙 비교와 출처 링크만 제공한다. 로고·집 아이콘·색/배치의 독창적 조합·안내 문장을 앱에 복제하지 않는다.

- 기록 영구삭제·정확한 보관/백업 정책, 실제 편집 스키마·저장 버그 해결, Gleo 직접 호출·권한·SDK·배포 승인·7초 동작은 별도 확인 대상이다.
- ‘구현 가능’은 로컬 C를 설계할 수 있다는 수준이며 이번 작업의 구현 완료가 아니다. A는 공식 방향의 지원, B는 근거 부족으로 보류한다.
- 게시 전 최신 main을 다시 확인하고 새 연구 파일만 추가한다. 동시 Codex 변경은 복원/삭제/덮어쓰기하지 않는다.
